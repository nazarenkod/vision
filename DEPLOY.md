# Vision: развёртывание и подключение тестов

Vision ставится на ту же машину, что и рабочий VRT, и работает на **копии** его базы и картинок.
Рабочий VRT продолжает работать как раньше; автотесты переключаются на Vision отдельным запуском,
когда вы решите.

## 0. Безопасность рабочего сервера

Что Vision делает с продом: **только читает**.

| Что | Как | Почему безопасно |
|---|---|---|
| База прода | `pg_dump` внутри контейнера прода (или по строке подключения) | pg_dump работает в транзакции только для чтения; запускается с наименьшим приоритетом CPU (`nice 19`) |
| Проверки перед копированием | несколько `SELECT`: имя и размер базы, есть ли таблицы VRT, список проектов, число пользователей | только чтение |
| Картинки прода | копирование (по умолчанию) или жёсткие ссылки (`PROD_IMAGES_MODE=link`) | файлы прода не открываются на запись. Vision пишет только новые файлы со случайными именами и никогда в существующие; удаление в Vision убирает только его копию или ссылку |

Что защищает от ошибок:
- **Все команды compose идут только через `./scripts/vision.sh`.** Имя проекта зашито (`vision`)
  и не берётся из `COMPOSE_PROJECT_NAME`, даже если она выставлена в shell.
- **Перед любой командой** скрипты проверяют, что все контейнеры проекта `vision` созданы из
  `docker-compose.demo.yml` этого репозитория. Если найден чужой контейнер (например, прод
  когда-то запущен с тем же именем проекта), не делается **ничего**.
- **Очистка базы** при копировании выполняется только в контейнере, который проверен как
  собственный Postgres Vision. Скрипт отказывается работать, если `PROD_PG_CONTAINER` указывает
  на контейнер Vision, а `PROD_IMAGES_DIR` — на папку Vision.
- **Диск.** Перед копированием и сборкой скрипты проверяют, что после операции останется не
  меньше 10 ГБ или 5% диска, что больше (`VISION_DISK_RESERVE_GB`). Если нет, ничего не
  делается: заполненный диск — главный способ навредить проду, стоящему рядом.
- **CPU и память Vision ограничены:** API — 2 CPU и 3 ГБ, сравнение картинок в 2 потока,
  Postgres — 1 CPU и 1 ГБ, UI — 0.5 CPU (настраивается в `.env.demo`).
- **Перед копированием** скрипт показывает, что прочитает и что заменит, и ждёт `yes`.

Проверено на стенде с upstream VRT 5.6.3 на postgres:12. Сняли «отпечаток» прода (хеши
содержимого всех таблиц, хеши всех картинок, время запуска контейнеров) до и после:
- отказов защиты (чужой проект `vision`, чужая `COMPOSE_PROJECT_NAME`);
- двух копирований (копия и ссылки);
- сборки и запуска;
- проверок из SDK и CLI;
- приёма прогонов и удаления сборок в Vision.

Отпечатки совпали полностью.

Что остаётся на вас:
- **Сборка образов** (шаг 5) несколько минут грузит CPU машины. Делайте её, когда прод не под
  пиковой нагрузкой.
- **pg_dump** большой базы держит долгую читающую транзакцию. Для VRT это безопасно, но лучше
  запускать копирование не в пик.
- **В режиме `link`** файлы, которые прод удалит при своей очистке, продолжают занимать место,
  пока на них ссылается Vision. Скрипт копирования можно запускать заново, чтобы обновить данные.
- **Никогда не указывайте** в `DEMO_*` и `POSTGRES_*` порты, базу или папки прода.

## 1. Что нужно

- Docker с Compose v2 (`docker compose version`), git, bash, rsync.
- Место на диске: около 6 ГБ под образы, плюс 2× размер базы, плюс размер картинок (в режиме
  `copy`). Скрипты посчитают сами.
- Свободные порты: 18080 (UI), 14200 (API), 15432 (Postgres, только localhost). Меняются в
  `.env.demo`.
- Имя Docker-контейнера с базой прода (`docker ps`) или строка подключения к ней.
- Папка картинок прода: то, что смонтировано в его API как `/imageUploads`. Если прод хранит
  картинки в S3, см. раздел 12.

Прод должен быть VRT 5.x и не новее форка. Скрипт проверит это сам.

## 3. Настройка

```bash
cp .env.demo.example .env.demo
```

Заполнить в `.env.demo`:

| Переменная | Что указать |
|---|---|
| `JWT_SECRET` | любой длинный секрет (можно тот же, что у прода: тогда у пользователей работают выданные токены входа) |
| `DEMO_UI_URL` | адрес UI так, как его видит браузер, например `http://vision-host:18080` |
| `DEMO_API_URL` | адрес API так, как его видит браузер и автотесты, например `http://vision-host:14200` |
| `PROD_PG_CONTAINER` | имя контейнера Postgres прода, **или** |
| `PROD_DATABASE_URL` | строка подключения к базе прода |
| `PROD_DB_NAME` | имя базы VRT в этом контейнере, если это не его `POSTGRES_DB`. Смотрите `DATABASE_URL` API прода: имя базы — после последнего `/`. Пусто — `POSTGRES_DB` |
| `PROD_IMAGES_DIR` | папка картинок прода |
| `PROD_IMAGES_MODE` | `copy` (по умолчанию) или `link` (без лишнего места, тот же диск) |

## 4. Копия данных прода

```bash
./scripts/demo-clone-from-prod.sh
```

Копируется **вся база VRT**: все проекты (iOS, Android и остальные), сборки, эталоны,
история, пользователи с паролями, API-ключи, настройки проектов. Перед подтверждением скрипт
показывает список проектов прода с числом сборок и эталонов, например:

```
  read from production:  database "vrt" (container vrt-postgres-1, 2.1 GB), read-only, all of it:
                         3 projects, 12 users
                           - Android app  (412 builds, 960 baselines)
                           - iOS app  (388 builds, 870 baselines)
                           - Web  (95 builds, 120 baselines)
```

Если выбранная база не содержит таблиц VRT (например, в том же Postgres живут другие
приложения, а `POSTGRES_DB` указывает не на VRT), скрипт остановится и покажет список баз на
сервере. Тогда укажите нужную в `PROD_DB_NAME`. После копирования скрипт сверяет число
проектов и пользователей в копии и в проде.

Скрипт покажет план и спросит `yes`. Дальше:
1. проверит место на диске и чужие контейнеры;
2. сделает `pg_dump` прода (только чтение) и восстановит дамп в Postgres Vision;
3. проверит, что прод — VRT 5.x и не новее форка;
4. скопирует или свяжет картинки.

Запускать можно повторно, чтобы взять свежие данные: всё, что сделано в Vision, заменится
текущим состоянием прода.

## 6. Настройки в Vision

Projects → карандаш у проекта:
- **Jira**: URL Jira. Токен у каждого свой: **Profile → Jira** (Server/DC — personal access
  token; Jira Cloud — API token и email). Баги заводятся от имени того, кто нажал кнопку, и
  Jira ищется с его правами. Общий токен в проекте теперь необязателен: он используется только
  для тех, кто свой ещё не добавил. Тогда из ревью можно заводить баги по
  доступности. Issue type и link type в настройках — только значения по умолчанию: при
  создании бага Vision берёт из Jira типы проекта задачи и показывает их списком, самый частый
  выбор подставляется сам.

#### Как создаётся баг

В ревью скриншота → вкладка Accessibility → **Create Jira bug** у проблемы, или **Create Jira
bugs for all N open problems** для всех открытых сразу. Указываете только задачу, она
запоминается для этого экрана. Дальше Vision:
- создаёт баг подзадачей этой задачи, если выбран тип-подзадача (как «Помилка»), или обычной
  задачей со связью выбранного типа;
- назначает исполнителя задачи;
- ставит серьёзность **S4** в поле вида «Серйозність помилки» / Severity;
- копирует из задачи «Замовника» и другие обязательные поля, которые знает задача;
- серьёзность, «Замовника» и обязательные поля, которые не заполнились сами, показывает в
  диалоге: людей можно найти по имени в Jira, варианты выбрать из списка. Выбор запоминается
  для проекта (например, «Замовник» для багов регресса);
- пишет описание по шаблону: сервіс / функціональний блок (название теста до первой точки),
  екран (`Appbar#Title` из page source, иначе название теста), фактичний і очікуваний результат,
  пристрій, елемент, правило, ссылка на ревью;
- прикладывает скриншот с обведённым проблемным элементом.

Перед созданием диалог показывает, что будет заполнено. Если Jira требует поле, которого Vision
не знает и которого нет в задаче, диалог называет его.

#### Только уникальные проблемы, без дублей

**ID проблемы** (`a11y-3f9c2a1b`) выдаётся один раз, при создании, и больше не меняется. Вместе
с ним проблема хранит факты тех мест, для которых её завели: правило, id элемента, компонент
(часть Compose tag после `#`, иначе resource id), экран, замер (зона тапа 38×38 dp, контраст
3.1), класс и подпись элемента.

**Что считать одной проблемой** решают настройки, и решают каждый раз заново поверх фактов —
и для новых находок, и для уже заведённых проблем. Поэтому смена настроек меняет группировку,
но не ID и не привязанные баги: если класс теперь склеивает `tab_0…tab_3`, а на них было два
бага, карточка покажет оба («Also filed for it»); если настройки разделили проблему, каждая
часть остаётся при своём баге. По умолчанию:
- элемент с id: правило + id компонента + замер (если включён для правила). Одинаковый id —
  одна проблема на всех экранах; другая зона тапа — уже другая проблема;
- элемент без id: правило + экран + элемент, между экранами не склеивается.

**ID экрана** — заголовок из UI-дерева (`id:Appbar#Title` по умолчанию, настраивается), иначе
название проверки.

**В Jira** у бага есть ID в конце summary и метки-маркеры фактов: `a11y-3f9c2a1b`,
`a11y-touch-target`, `a11y-component-PbButton`, `a11y-value-38x38`, `a11y-class-…`. Если на экране
создания нет поля Labels (как у «Помилка»), метки ставятся отдельным редактированием. Vision
ищет баг по ID **или по комбинации маркеров**, которыми текущие настройки отличают проблемы.
Так находятся баги, заведённые до смены настроек, другой инсталляцией или руками (достаточно
поставить маркеры). Поиск в Jira руками: `labels = a11y-3f9c2a1b` или, например,
`labels = a11y-touch-target AND labels = a11y-component-PbButton`.

**Как Vision не даёт завести дубль:**
- перед созданием атомарно «занимает» проблему в базе: второй человек получит «уже заведено как
  KEY» (и привяжет его) или «прямо сейчас заводит другой»;
- там же ищет в Jira по ID и маркерам: открытый баг привязывает вместо создания, только
  закрытый — предупреждает и заводит новый;
- при открытии ревью одним-двумя JQL-запросами проверяет незаведённые проблемы экрана и
  найденные помечает как заведённые (ответ кешируется на 10 минут, таймаут 5 секунд).

**Решения и журнал.** Каждое решение пишется в журнал (`A11yDecision`): кто и когда завёл,
привязал, отвязал, нашёл в Jira, пометил false positive или вернул.
- **Link existing** ставит на баг маркеры проблемы.
- **Unlink** снимает с бага маркеры Vision и ставит `a11y-unlinked-3f9c2a1b`; отвязанный баг
  поиск больше никогда не привяжет сам (по журналу и по этой метке), пока его не привяжут
  руками. Если проблема, решённая по прежним настройкам, теперь разделилась, Unlink убирает
  только эту часть, остальное остаётся при баге, и в Jira ничего не меняется.

**Настройки** (Projects → карандаш → Accessibility, спецификация 026):
- каждое из 7 правил можно выключить; его находки пропадают из ревью, счётчиков, Insights, CLI и MCP;
- *Minimum touch target* — нормы проекта для Android (dp) и iOS (pt), по умолчанию 48 и 44;
- *Minimum contrast* — для обычного и крупного текста, по умолчанию 4.5 и 3.

Более мягкая норма скрывает находки и на уже полученных снимках; более строгая находит новые
только на следующих снимках. После сохранения настроек счётчики 5 последних билдов
пересчитываются в фоне. Заголовок экрана (`id:Appbar#Title`) в интерфейсе не настраивается;
селекторы, сохранённые раньше, продолжают работать.

Что считать одной проблемой, не настраивается (спецификация 021): зона тапа и контраст — тот же
компонент и то же значение на любом экране; остальные правила — тот же компонент; одинаковая
подпись — в пределах экрана; элемент без id — проблема только своего экрана. Режимы и классы,
сохранённые раньше, остаются в настройках проекта, но не читаются.

Решения, принятые до этой версии, переносятся при старте API (в логе: «Moved N accessibility
decisions to problems»).

### Insights

Левое меню → **Insights** (у выбранного проекта), период 30–365 дней:
- **неиспользуемые эталоны:** с ними ничего не сравнивалось за период; есть массовое удаление с подтверждением;
- **нестабильные экраны** и «мигания»: экран отличался, а следующий прогон снова совпал с тем же эталоном, то есть «прыгает» экран, а не приложение;
- **доступность:** худшие экраны и самые частые проблемы;
- **шум:** мелкие изменения, которые раз за разом принимают;
- **съёмка во время загрузки** и скрытые изменения;
- **покрытие:** каких проверок не хватает на каждом устройстве;
- **очередь ревью:** сколько прогонов ждёт решения и медианное время до решения.

Если проект хранит не всю историю (лимит сборок удалил старые), страница предупреждает и
считает «неиспользуемыми» относительно того, что осталось. Удаление в Vision не затрагивает
прод: это копия.

## 7. SDK: jar и pom.xml

**Пока ничего менять не нужно.** Vision понимает текущий SDK как есть: скриншоты, статусы, группы
изменений работают. Новый SDK нужен только для отправки XML-дерева экрана: доступность,
изменения по элементам, правила по элементам, а также для названия фичи в багах из сравнения.

Новый SDK — это upstream 4.3.1 плюс два необязательных поля: `uiTree` и `featureName`. Пакет и классы те же,
работает на Java 11+. Готовый jar лежит в репозитории: `dist/sdk-java/sdk-java-4.3.1-vision.2.jar`
(рядом его pom). Пересобрать: `./scripts/build-sdk-jar.sh` (JDK 11–17, Gradle 7).

### Обновление с 4.3.1-vision.1

Что нового в `4.3.1-vision.2`: необязательное поле `featureName` — фича экрана для названия бага,
заведённого из сравнения: `[Automation] [Checkout] кнопка обрезана`. Без него Vision берёт часть
названия проверки до первой точки (`Checkout. Payment sheet` → `Checkout`). Эталоны от поля не
зависят: прогоны с ним и без него сравниваются с теми же эталонами.

Обновляться не обязательно: `vision.1` продолжает работать, сервер принимает запросы без
`featureName`. Чтобы обновиться:

1. Вариант А: ещё раз `mvn install:install-file` с файлами `vision.2` (команда ниже) и версия
   `4.3.1-vision.2` в pom.xml. Вариант Б: заменить jar в `libs/` и поправить версию и `systemPath`.
2. Если названия проверок не начинаются с фичи, добавить `.featureName(...)` в обёртку над
   `vrt.track` (пример в 8.2). Больше в тестах ничего не меняется.

### Вариант А: установить в локальный Maven (рекомендую)

Один раз на каждой машине, где собираются тесты (ноутбук, агенты CI):

```bash
mvn install:install-file -Dfile=dist/sdk-java/sdk-java-4.3.1-vision.2.jar -DpomFile=dist/sdk-java/sdk-java-4.3.1-vision.2.pom
```

В pom.xml меняется только версия:

```xml
<dependency>
    <groupId>com.github.Visual-Regression-Tracker</groupId>
    <artifactId>sdk-java</artifactId>
    <version>4.3.1-vision.2</version>
</dependency>
```

Зависимости SDK (gson, slf4j) подтянутся сами из pom, который установился вместе с jar.

### Вариант Б: jar внутри проекта тестов

Положить jar в `libs/` проекта тестов и закоммитить. Тогда ничего устанавливать не нужно:

```xml
<dependency>
    <groupId>com.github.Visual-Regression-Tracker</groupId>
    <artifactId>sdk-java</artifactId>
    <version>4.3.1-vision.2</version>
    <scope>system</scope>
    <systemPath>${project.basedir}/libs/sdk-java-4.3.1-vision.2.jar</systemPath>
</dependency>
<!-- jar из файла не приносит своих зависимостей; если они уже есть в проекте, эти две не нужны -->
<dependency>
    <groupId>com.google.code.gson</groupId>
    <artifactId>gson</artifactId>
    <version>2.9.0</version>
</dependency>
<dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-api</artifactId>
    <version>1.7.25</version>
</dependency>
```

Maven предупредит о `system` scope, это нормально.

Оба варианта проверены Maven-проектом на `vision.1`: собирается и отправляет экраны с XML в
Vision. `vision.2` отличается от неё только полем `featureName`; его покрывают тесты SDK
(`gradle test`), Maven-проектом его ещё не прогоняли.
Публикация в Nexus тоже настроена (`gradle publish -PrepoUrl=...`, см. `sdk-java/README.md`),
пригодится, когда захотите убрать ручной шаг.

## 8. Подключение автотестов

### 8.1. Куда отправлять

Адрес и ключ задаются переменными окружения, код для этого менять не нужно:

```bash
export VRT_APIURL=http://vision-host:14200
```

```bash
export VRT_APIKEY=ваш_API_ключ
```

`VRT_PROJECT` и `VRT_BRANCHNAME` — как сейчас. Ключ тот же, что на проде: он скопирован.

Переменные работают, только если адрес и ключ **не заданы в коде**. SDK берёт значение из
`VisualRegressionTrackerConfig.builder().apiUrl(...)`, если оно там есть, затем из
переменной `VRT_APIURL`, затем из `vrt.json`. Если в коде стоит `.apiUrl("http://vrt-prod...")`,
вынесите его в переменную или системное свойство, например
`.apiUrl(System.getenv().getOrDefault("VRT_APIURL", "http://vrt-prod:4200"))`.

Рабочий прогон не трогайте. Для Vision сделайте **отдельную джобу**: тот же набор тестов с
этими двумя переменными. Прод продолжит получать свои прогоны, Vision будет получать свои.

### 8.2. Добавить XML экрана

Java:

```java
vrt.track(
    "Payment",
    screenshotBase64,
    TestRunOptions.builder()
        .device("Pixel 7 emulator")
        .os("Android 15")
        .uiTree(WebDriverRunner.getWebDriver().getPageSource())
        .featureName("Checkout")   // необязательно: фича для названия бага
        .build()
);
```

Kotlin:

```kotlin
vrt.track(
    "Payment",
    screenshotBase64,
    TestRunOptions.builder()
        .device("Pixel 7 emulator")
        .os("Android 15")
        .uiTree(WebDriverRunner.getWebDriver().pageSource)
        .featureName("Checkout")   // необязательно: фича для названия бага
        .build()
)
```

Если у вас обёртка над `vrt.track`, правка одна, в ней. Без `.uiTree(...)` всё работает как
раньше. `featureName` попадает в название бага из сравнения (`[Automation] [Checkout] …`); без него
Vision берёт часть названия проверки до первой точки. Эталоны от него не зависят.

### 8.3. Правила, о которых стоит помнить

- **Название проверки** — главный ключ. Состояния экрана — отдельные проверки:
  `Payment`, `Payment – error`, `Payment – bottom sheet`.
- **device и os** задают эталон устройства. Передавайте их стабильно, как сейчас: эмулятор
  и устройство из BrowserStack — разные эталоны одной проверки.
- **iOS и Android** — разные проекты, как у вас сейчас. Эталонное устройство выбирается в
  каждом проекте отдельно.
- **Новое устройство** приходит со статусом «new»: примите его один раз, и у него появится
  свой эталон.

### 8.4. Разрешённые устройства

Чтобы эталоны не появлялись для эмуляторов, на которых CI не гоняется, в настройках проекта есть
раздел **Devices**: список «устройство + версия OS». Пока он пуст, принимаются снимки с любого
устройства. Как только в нём есть хоть одна запись, снимок из SDK с другого устройства или другой
версии OS отклоняется, и `track` падает (даже с soft assert):

```
TestRunException: {"path":"/test-runs","name":"UnprocessableEntityException","message":"Device not allowed in project \"AOS\": check \"Payment\" was sent from device \"Pixel 6\", OS \"Android 13\". Allowed: \"Pixel 7 emulator\" / \"Android 15\". Run on an allowed device or add it in Project settings > Devices.", ...}
```

Порядок включения:

1. Откройте **Settings → Devices**. Под списком — «Devices from snapshots»: устройства ровно в том
   виде, в каком их уже присылают тесты. Сначала добавьте кнопкой **Add** те, на которых гоняется
   CI, — иначе упадёт весь прогон.
2. Для BrowserStack, который сам выбирает минорную версию, укажите `26.*`: подойдут `26`, `26.1`,
   `26.2.1`, но не `27.0`. `*` в другом месте не сохранится.
3. Регистр и пробелы по краям не важны. Ручные проверки из CLI и MCP список не ограничивает.

## 9. Ручные проверки

В Vision: меню «?» → **Manual checks (CLI)**. Там три готовые команды с ключом пользователя:

```bash
curl -fsSLO http://vision-host:18080/cli/vision.py
```

```bash
python3 vision.py config --api http://vision-host:14200 --key КЛЮЧ --project "Mobile app"
```

```bash
python3 vision.py check "Payment"
```

- **Источники экрана:**
  - подключённое Android-устройство или эмулятор (adb);
  - `--appium http://127.0.0.1:4723` — Appium-сессия, Android или iOS;
  - `--simulator` — iOS-симулятор, только скриншот;
  - `--png файл.png --xml файл.xml` — готовые файлы.
- **Несколько экранов в одну сборку:** `start` / `finish`.
- **Ветка:** проверки идут в ветку `manual` и сравниваются с эталонами основной ветки.
- **Эталоны автотестов:** чтобы сравнивать с ними попиксельно, добавьте в `config`
  `--device` и `--os`, названные так же, как в автотестах.
- **Права:** для отправки нужна роль editor или admin.
- **Окружение:** Python 3.8+, без пакетов.
- **Для AI-ассистентов** — MCP: `python3 vision.py mcp`.

## 12. Бэкапы

Каждую ночь база Vision и новые картинки уходят в папку `vision-backups` на «Моём диске» Google
Drive рабочего аккаунта администратора ([013](docs/specs/013-backups-and-secrets/spec.md),
[017](docs/specs/017-backup-settings-ui/spec.md)). Бэкап не шифруется, поэтому в нём **нет
паролей и токенов Jira**; API-ключи есть, чтобы автотесты после восстановления работали без
изменений. Vision видит на этом Drive только файлы, которые создал сам.

Нужен доступ сервера к `oauth2.googleapis.com`, `www.googleapis.com` и Docker Hub. rclone
ставить не нужно: скрипты запускают Docker-образ `rclone/rclone:1.68.2`, если rclone нет на
сервере.

### Настроить один раз

1. **OAuth-клиент** в [Google Cloud Console](https://console.cloud.google.com), в проекте банка
   (подробно, с ошибками и почему так — [google-drive-access](docs/guides/google-drive-access.md)):
   - «APIs & Services» → «Library» → **Google Drive API** → «Enable»;
   - «OAuth consent screen» (или «Google Auth Platform») → тип **Internal**, название `Vision
     backups`. Если Internal недоступен, проект создан вне организации банка: создайте его в ней.
     У типа External в режиме Testing доступ пропадает через 7 дней;
   - «Credentials» → «Create credentials» → «OAuth client ID» → тип **TVs and Limited Input
     devices** → «Create». Сохраните Client ID и Client secret.
2. **`.env.demo`** — мастер-логин для входа после восстановления:

   ```bash
   VISION_MASTER_EMAIL=ваш_email
   VISION_MASTER_PASSWORD=не_короче_12_символов
   ```

   Сохраните их копию **вне** сервера: на новой машине их придётся ввести снова.
3. **Обновить Vision и поставить расписание:**

   ```bash
   ./scripts/vision.sh up -d --build
   ```

   ```bash
   ./scripts/vision-backup.sh --install-cron
   ```

   cron раз в 5 минут проверяет, не пора ли делать бэкап и не просили ли его на странице Backups.
   Журнал — `demo-data/backups/cron.log`. Пользователю, который ставит cron, нужен доступ к `docker`.
4. **В Vision** под администратором: меню аккаунта → **Backups** → «Google Drive» → вставить
   Client ID и Client secret → «Connect» → открыть показанную ссылку (google.com/device) на любом
   устройстве, войти рабочим аккаунтом, ввести код и разрешить доступ. Страница покажет
   «Connected as …».
5. На той же странице: «Test connection», при желании время и число копий в «Schedule», затем
   **«Back up now»**. В течение 5 минут бэкап появится в списке «In Google Drive».

На Drive хранятся последние дампы базы (7, меняется в «Schedule») и картинки, которые нужны хотя бы
одному из них: новые докачиваются, а картинка удалённого в Vision эталона пропадает с Drive вместе с
последним дампом, где она ещё была (примерно через неделю). Локальные картинки не трогаются. Если Drive недоступен, бэкап остаётся в `demo-data/backups` и уходит при следующем
запуске. Если последнему успешному бэкапу больше 26 часов, администраторы видят предупреждение
со ссылкой на страницу Backups. `demo-clone-from-prod.sh` сам делает бэкап перед тем, как
заменить непустую базу Vision.

Без интерфейса можно и по-старому: `BACKUP_REMOTE=имя_remote:папка` в `.env.demo` и конфиг rclone в
`RCLONE_CONFIG_DIR` (по умолчанию `~/.config/rclone`). Подключение на странице Backups важнее.

### Восстановить

```bash
./scripts/vision-restore.sh
```

Берёт последний бэкап (или указанный: `./scripts/vision-restore.sh vision-20261027T031700Z.tar`),
показывает план и ждёт `yes`. На чистой машине: §2–3 (код и `.env.demo`), шаги 1–3 выше, войти
пользователем по умолчанию пустого Vision (`DEFAULT_USER_EMAIL` / `DEFAULT_USER_PASSWORD` из
`.env.demo`; если не заданы — `visual-regression-tracker@example.com` / `123456`), подключить Drive
на странице Backups тем же рабочим аккаунтом и тем же OAuth-клиентом (Vision видит только файлы
своего клиента), затем restore:
подключение лежит в `demo-data/backup-config` и восстановлением базы не затирается.

После восстановления:
- входите мастер-логином; он становится администратором;
- остальным пользователям задайте пароль: Users → выделить пользователя → «Set password»;
- токены Jira каждый вводит заново в профиле, общий токен проекта — администратор;
- API-ключи и автотесты — без изменений.

## 13. Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| «containers that were not created from …» | в проекте `vision` есть чужие контейнеры. Скрипт ничего не сделал. Выясните, чьи они (`docker ps -a --filter label=com.docker.compose.project=vision`), не удаляйте вслепую |
| «Not enough disk …» | освободите место (`docker system df`, `docker builder prune`) или, для картинок, `PROD_IMAGES_MODE=link` |
| «production VRT is older than 5.x» | сначала обновите прод, или запускайте Vision на пустой базе (без шага 4) |
| «Production has migrations this fork does not know» | прод новее форка: нужно подтянуть upstream в форк |
| `migration` в состоянии Exited (1) | `./scripts/vision.sh logs migration` |
| Не работает вход | `DEMO_API_URL` должен открываться из браузера; `./scripts/vision.sh logs api` |
| У старых прогонов нет картинок | `PROD_IMAGES_DIR` указывал не туда: исправить и повторить шаг 4 |
| Прод хранит картинки в S3 | скопируйте бакет в **отдельный** бакет и укажите его API Vision теми же переменными `AWS_*`, что у прода. Бакет прода Vision указывать нельзя: Vision удаляет старые картинки |
