# Vision: розгортання й підключення тестів

Vision ставиться на ту саму машину, що й робочий VRT, і працює на **копії** його бази й картинок.
Робочий VRT працює далі як раніше; автотести перемикаються на Vision окремим запуском,
коли ви вирішите.

## 0. Безпека робочого сервера

Що Vision робить із продом: **лише читає**.

| Що | Як | Чому безпечно |
|---|---|---|
| База проду | `pg_dump` усередині контейнера проду (або за рядком підключення) | pg_dump працює в транзакції лише на читання; запускається з найнижчим пріоритетом CPU (`nice 19`) |
| Перевірки перед копіюванням | кілька `SELECT`: назва й розмір бази, чи є таблиці VRT, список проєктів, кількість користувачів | лише читання |
| Картинки проду | копіювання (за замовчуванням) або жорсткі посилання (`PROD_IMAGES_MODE=link`) | файли проду не відкриваються на запис. Vision пише лише нові файли з випадковими назвами й ніколи в наявні; видалення у Vision прибирає лише його копію або посилання |

Що захищає від помилок:
- **Усі команди compose йдуть лише через `./scripts/vision.sh`.** Назву проєкту зашито (`vision`)
  і вона не береться з `COMPOSE_PROJECT_NAME`, навіть якщо її виставлено в shell.
- **Перед будь-якою командою** скрипти перевіряють, що всі контейнери проєкту `vision` створено з
  `docker-compose.demo.yml` цього репозиторію. Якщо знайдено чужий контейнер (наприклад, прод
  колись запустили з тією самою назвою проєкту), не робиться **нічого**.
- **Очищення бази** під час копіювання виконується лише в контейнері, який перевірено як
  власний Postgres Vision. Скрипт відмовляється працювати, якщо `PROD_PG_CONTAINER` вказує
  на контейнер Vision, а `PROD_IMAGES_DIR` — на папку Vision.
- **Диск.** Перед копіюванням і збиранням скрипти перевіряють, що після операції залишиться не
  менше ніж 10 ГБ або 5% диска, що більше (`VISION_DISK_RESERVE_GB`). Якщо ні, нічого не
  робиться: заповнений диск — головний спосіб нашкодити проду, що стоїть поруч.
- **CPU і пам'ять Vision обмежено:** API — 2 CPU і 3 ГБ, порівняння картинок у 2 потоки,
  Postgres — 1 CPU і 1 ГБ, UI — 0.5 CPU (налаштовується в `.env.demo`). Пошук позначених шматків
  нестабільного тексту на знімку (OCR, [ADR-0031](docs/decisions/0031-ocr-to-locate-variable-text.md))
  займає в API ще ~150 МБ, лише коли є такі правила, і не більше 5 с CPU на рядок.
- **Перед копіюванням** скрипт показує, що прочитає і що замінить, і чекає `yes`.

Перевірено на стенді з VRT 5.6.3 на postgres:12. Зняли «відбиток» проду (хеші
вмісту всіх таблиць, хеші всіх картинок, час запуску контейнерів) до і після:
- відмов захисту (чужий проєкт `vision`, чужа `COMPOSE_PROJECT_NAME`);
- двох копіювань (копія й посилання);
- збирання й запуску;
- перевірок із SDK і CLI;
- прийому прогонів і видалення збірок у Vision.

Відбитки збіглися повністю.

Що залишається на вас:
- **Збирання образів** (крок 5) кілька хвилин навантажує CPU машини. Робіть його, коли прод не під
  піковим навантаженням.
- **pg_dump** великої бази тримає довгу транзакцію на читання. Для VRT це безпечно, але краще
  запускати копіювання не в пік.
- **У режимі `link`** файли, які прод видалить під час свого очищення, і далі займають місце,
  поки на них посилається Vision. Скрипт копіювання можна запускати знову, щоб оновити дані.
- **Ніколи не вказуйте** в `DEMO_*` і `POSTGRES_*` порти, базу чи папки проду.

## 1. Що потрібно

- Docker із Compose v2 (`docker compose version`), git, bash, rsync.
- Місце на диску: близько 6 ГБ під образи, плюс 2× розмір бази, плюс розмір картинок (у режимі
  `copy`). Скрипти порахують самі.
- Вільні порти: 18080 (UI), 14200 (API); Postgres назовні не публікується. Змінюються в
  `.env.demo`.
- Назва Docker-контейнера з базою проду (`docker ps`) або рядок підключення до неї.
- Папка картинок проду: те, що змонтовано в його API як `/imageUploads`. Якщо прод зберігає
  картинки в S3, див. розділ 12.

Прод має бути VRT 5.x і не новіший за форк. Скрипт перевірить це сам.

Образи збираються з цього репозиторію на Node 24 (базу закріплено за digest), усі процеси
працюють не від root: API — від користувача, який запускає `vision.sh`, UI — від `nginx`.
TLS перевіряється завжди. У закритій мережі (проксі перепідписує TLS, немає доступу до
registry.npmjs.org або binaries.prisma.sh) задайте в `.env.demo` `VISION_EXTRA_CA_FILE` (CA
проксі, PEM), `VISION_NPM_REGISTRY` і `VISION_PRISMA_ENGINES_MIRROR` — дзеркала, наприклад у Nexus.

## 3. Налаштування

```bash
cp .env.demo.example .env.demo
```

Заповнити в `.env.demo`:

| Змінна | Що вказати |
|---|---|
| `JWT_SECRET` | новий випадковий секрет (`openssl rand -base64 32`), **не** секрет робочого VRT: зі спільним секретом вхід у Vision відкривав би й робочий VRT. API не стартує зі значенням із прикладу, із секретом, коротшим за 32 символи, і з тим самим значенням, що в `VISION_SECRET_KEY` ([051](docs/specs/051-security-quick-fixes/spec.md)) |
| `VISION_SECRET_KEY` | довгий випадковий ключ (`openssl rand -base64 32`), **зберігати назавжди**: ним зашифровано токени Jira і ключі Gemini в базі. Без нього API не стартує; новий ключ — усі вводять токени заново ([044](docs/specs/044-secrets-at-rest/spec.md)). Ті самі вимоги, що й до `JWT_SECRET` ([051](docs/specs/051-security-quick-fixes/spec.md)) |
| `VISION_JIRA_HOSTS` | хости Jira через кому, куди можна надсилати особисті токени, наприклад `jira.example.com`: токен іде лише по `https` на стандартний порт і не йде за переадресацією. Jira на іншому порту або по `http` — запис зі схемою й портом, наприклад `https://jira.example.com:8443` ([051](docs/specs/051-security-quick-fixes/spec.md)). Порожньо — Vision у Jira не ходить, а адресу Jira в проєкті не зберегти |
| `DEFAULT_USER_PASSWORD` | пароль першого адміністратора (`DEFAULT_USER_EMAIL`, типово `admin@vision.local`), щонайменше 12 символів. Потрібен лише порожній базі: копія проду приходить зі своїми адмінами. Типового пароля немає: без нього міграція зупиняється й API не стартує ([082](docs/specs/082-fortify-readiness/spec.md)) |
| `DEMO_UI_URL` | адреса UI так, як її бачить браузер, наприклад `http://vision-host:18080` |
| `DEMO_API_URL` | адреса API так, як її бачать браузер і автотести, наприклад `http://vision-host:14200` |
| `PROD_PG_CONTAINER` | назва контейнера Postgres проду, **або** |
| `PROD_DATABASE_URL` | рядок підключення до бази проду |
| `PROD_DB_NAME` | назва бази VRT у цьому контейнері, якщо це не його `POSTGRES_DB`. Дивіться `DATABASE_URL` API проду: назва бази — після останнього `/`. Порожньо — `POSTGRES_DB` |
| `PROD_IMAGES_DIR` | папка картинок проду |
| `PROD_IMAGES_MODE` | `copy` (за замовчуванням) або `link` (без зайвого місця, той самий диск) |

## 4. Копія даних проду

```bash
./scripts/demo-clone-from-prod.sh
```

Копіюється **уся база VRT**: усі проєкти (iOS, Android та інші), збірки, еталони,
історія, користувачі з паролями, API-ключі, налаштування проєктів. Перед підтвердженням скрипт
показує список проєктів проду з кількістю збірок і еталонів, наприклад:

```
  read from production:  database "vrt" (container vrt-postgres-1, 2.1 GB), read-only, all of it:
                         3 projects, 12 users
                           - Android app  (412 builds, 960 baselines)
                           - iOS app  (388 builds, 870 baselines)
                           - Web  (95 builds, 120 baselines)
```

Якщо вибрана база не містить таблиць VRT (наприклад, у тому самому Postgres живуть інші
застосунки, а `POSTGRES_DB` вказує не на VRT), скрипт зупиниться й покаже список баз на
сервері. Тоді вкажіть потрібну в `PROD_DB_NAME`. Після копіювання скрипт звіряє кількість
проєктів і користувачів у копії та в проді.

Скрипт покаже план і спитає `yes`. Далі:
1. перевірить місце на диску й чужі контейнери;
2. зробить `pg_dump` проду (лише читання) і відновить дамп у Postgres Vision;
3. перевірить, що прод — VRT 5.x і не новіший за форк;
4. скопіює або зв'яже картинки.

Запускати можна повторно, щоб узяти свіжі дані: усе, що зроблено у Vision, заміниться
поточним станом проду.

## 5. Запуск і перевірка

```bash
./scripts/vision.sh up -d --build
```

```bash
./scripts/vision.sh ps -a
```

Має бути: `migration` — **Exited (0)**, а `api`, `ui` і `postgres` — **Up**.

```bash
curl -s http://localhost:14200/health
```

Відповідь `{"status":"ok",...}`. У лозі міграцій наприкінці має бути `All migrations have been
successfully applied`:

```bash
./scripts/vision.sh logs migration
```

Відкрити `DEMO_UI_URL` і ввійти **продовим** обліковим записом. Користувачів, паролі, проєкти й збірки
скопійовано. **API-ключі VRT у Vision не діють** ([044](docs/specs/044-secrets-at-rest/spec.md)):
під час першого старту API робить їх недійсними, кожен створює новий у **Profile → API key**
і прописує його в CI (`VISION_APIKEY` або `vision.json`). Ключ показується один раз.

**Доступ до проєктів** ([042](docs/specs/042-project-access/spec.md)): після переходу кожен бачить
усі проєкти, як раніше. Адмін звужує доступ у **Settings проєкту → Access**; нові користувачі
проєктів не бачать, доки адмін не дасть. Editor, який створив проєкт, бачить його одразу.

## 6. Налаштування у Vision

**Вхід** ([045](docs/specs/045-sign-in-and-api-hardening/spec.md)). LDAP або SSO вмикаються в `.env.demo`
(`LDAP_*` або `OIDC_*`, приклад — у `.env.demo.example`; сертифікат сервера входу перевіряється
завжди, внутрішній CA — у `VISION_EXTRA_CA_FILE`, [082](docs/specs/082-fortify-readiness/spec.md)), і локальні акаунти від адміна працюють
поруч: LDAP вирішує за тих, хто є в каталозі, інші входять своїм паролем; із SSO форма пароля —
під кнопкою SSO, а з `REACT_APP_OIDC_AUTO_REDIRECT` — за адресою `/login?local`. Пароль локального
акаунта — від 12 символів; 5 невдалих спроб поспіль закривають вхід для цього email на 15 хвилин.
Документацію API (`/api`) вимкнено, доки `VISION_SWAGGER=true`.

**Сеанси й браузер** ([052](docs/specs/052-sessions-and-browser-hardening/spec.md)). «Вийти»
завершує вхід у цьому браузері на сервері: скопійований токен більше нічого не відкриває. Зміна
пароля завершує інші входи людини, пароль від адміна — усі; API-ключів SDK і CLI це не
стосується. З SSO роль `editor` або `guest`, задана адміном, після входу зберігається; адміном
робить лише група з `OIDC_ADMIN_VALUES`. Інтерфейс і API віддають політику CSP; адреса API в неї
підставляється під час старту контейнера `ui` з `DEMO_API_URL`. Vision працює по http без сертифіката;
якщо перед ним буде проксі з https, він має передавати `X-Forwarded-Proto: https` — тоді
відповіді отримують HSTS (браузер рік ходить лише по https). Образи `ui` і `api` оновлюються
разом (`./scripts/vision.sh` так і робить): новий інтерфейс зі старим API не пускає через SSO.
Плитка SSO на порталі може вести просто на `<API>/users/oidc/login` — Vision сам відкриє свою
сторінку входу й продовжить.

Projects → олівець біля проєкту:
- **Jira**: URL Jira — лише на хості з `VISION_JIRA_HOSTS`. Токен у кожного свій: **Profile → Jira** (Server/DC — personal access
  token; Jira Cloud — API token і email). Баги заводяться від імені того, хто натиснув кнопку, і
  Jira шукається з його правами. Спільного токена проєкту немає ([035](docs/specs/035-admin-accounts/spec.md)):
  без свого токена баг не завести. Спільні токени, збережені раніше, Vision стирає під час
  першого старту нової версії, тому **перед оновленням** попросіть команду додати свої
  токени в профіль. Issue type і link type у налаштуваннях вибираються зі списку, який Vision
  бере з Jira з токеном того, хто відкрив налаштування; це лише значення за замовчуванням: під час
  створення бага Vision бере з Jira типи проєкту задачі й показує їх списком, найчастіший
  вибір підставляється сам.

#### Як створюється баг

У рев'ю скриншота → вкладка Accessibility → **Create Jira bug** біля проблеми, або **Create Jira
bugs for all N open problems** для всіх відкритих одразу. Вказуєте лише задачу, вона
запам'ятовується для цього екрана. Далі Vision:
- створює баг підзадачею цієї задачі, якщо вибрано тип-підзадачу (як «Помилка»), або звичайною
  задачею зі зв'язком вибраного типу;
- призначає виконавця задачі;
- ставить серйозність **S4** у поле на кшталт «Серйозність помилки» / Severity;
- копіює із задачі «Замовника» та інші обов'язкові поля, які знає задача;
- серйозність, «Замовника» й обов'язкові поля, які не заповнилися самі, показує в
  діалозі: людей можна знайти за іменем у Jira, варіанти вибрати зі списку. Вибір запам'ятовується
  для проєкту (наприклад, «Замовник» для багів регресу);
- пише опис за шаблоном: сервіс / функціональний блок (назва тесту до першої крапки),
  екран (`Appbar#Title` із page source, інакше назва тесту), фактичний і очікуваний результат,
  пристрій, елемент, правило, посилання на рев'ю;
- додає скриншот з обведеним проблемним елементом.

Перед створенням діалог показує, що буде заповнено. Якщо Jira вимагає поле, якого Vision
не знає і якого немає в задачі, діалог називає його.

#### Лише унікальні проблеми, без дублів

**ID проблеми** (`a11y-3f9c2a1b`) видається один раз, під час створення, і більше не змінюється. Разом
із ним проблема зберігає факти тих місць, для яких її завели: правило, id елемента, компонент
(частина Compose tag після `#`, інакше resource id), екран, вимір (зона тапу 38×38 dp, контраст
3.1), клас і підпис елемента.

**Що вважати однією проблемою**, вирішують налаштування, і вирішують щоразу заново поверх фактів —
і для нових знахідок, і для вже заведених проблем. Тому зміна налаштувань змінює групування,
але не ID і не прив'язані баги: якщо клас тепер склеює `tab_0…tab_3`, а на них було два
баги, картка покаже обидва («Also filed for it»); якщо налаштування розділили проблему, кожна
частина залишається при своєму багу. За замовчуванням:
- елемент з id: правило + id компонента + вимір (якщо ввімкнено для правила). Однаковий id —
  одна проблема на всіх екранах; інша зона тапу — уже інша проблема;
- елемент без id: правило + екран + елемент, між екранами не склеюється.

**ID екрана** — заголовок з UI-дерева (`id:Appbar#Title` за замовчуванням, налаштовується), інакше
назва перевірки.

**У Jira** баг має ID в кінці summary і мітки-маркери фактів: `a11y-3f9c2a1b`,
`a11y-touch-target`, `a11y-component-PbButton`, `a11y-value-38x38`, `a11y-class-…`. Якщо на екрані
створення немає поля Labels (як у «Помилка»), мітки ставляться окремим редагуванням. Vision
шукає баг за ID **або за комбінацією маркерів**, якими поточні налаштування розрізняють проблеми.
Так знаходяться баги, заведені до зміни налаштувань, іншою інсталяцією або вручну (досить
поставити маркери). Пошук у Jira вручну: `labels = a11y-3f9c2a1b` або, наприклад,
`labels = a11y-touch-target AND labels = a11y-component-PbButton`.

**Як Vision не дає завести дубль:**
- перед створенням атомарно «займає» проблему в базі: друга людина отримає «уже заведено як
  KEY» (і прив'яже його) або «саме зараз заводить інший»;
- там само шукає в Jira за ID і маркерами: відкритий баг прив'язує замість створення, лише
  про закритий — попереджає й заводить новий;
- під час відкриття рев'ю одним-двома JQL-запитами перевіряє незаведені проблеми екрана й
  знайдені позначає як заведені (відповідь кешується на 10 хвилин, тайм-аут 5 секунд).

**Рішення і журнал.** Кожне рішення пишеться в журнал (`A11yDecision`): хто й коли завів,
прив'язав, відв'язав, знайшов у Jira, позначив false positive або повернув.
- **Link existing** ставить на баг маркери проблеми.
- **Unlink** знімає з бага маркери Vision і ставить `a11y-unlinked-3f9c2a1b`; відв'язаний баг
  пошук більше ніколи не прив'яже сам (за журналом і за цією міткою), доки його не прив'яжуть
  вручну. Якщо проблема, вирішена за попередніми налаштуваннями, тепер розділилася, Unlink прибирає
  лише цю частину, решта залишається при багу, і в Jira нічого не змінюється.

**Налаштування** (Projects → олівець → Accessibility, специфікація 026):
- кожне із 7 правил можна вимкнути; його знахідки зникають з рев'ю, лічильників, Insights, CLI і MCP;
- *Minimum touch target* — норми проєкту для Android (dp) та iOS (pt), за замовчуванням 48 і 44;
- *Minimum contrast* — для звичайного й великого тексту, за замовчуванням 4.5 і 3.

М'якша норма приховує знахідки й на вже отриманих знімках; суворіша знаходить нові
лише на наступних знімках. Після збереження налаштувань лічильники 5 останніх збірок
перераховуються у фоні. Заголовок екрана (`id:Appbar#Title`) в інтерфейсі не налаштовується;
селектори, збережені раніше, і далі працюють.

Що вважати однією проблемою, не налаштовується (специфікація 021): зона тапу й контраст — той самий
компонент і те саме значення на будь-якому екрані; інші правила — той самий компонент; однаковий
підпис — у межах екрана; елемент без id — проблема лише свого екрана. Режими й класи,
збережені раніше, залишаються в налаштуваннях проєкту, але не читаються.

Рішення, ухвалені до цієї версії, переносяться під час старту API (у лозі: «Moved N accessibility
decisions to problems»).

### Insights

Ліве меню → **Insights** (для вибраного проєкту), період 30–365 днів:
- **невикористані еталони:** із ними нічого не порівнювалося за період; є масове видалення з підтвердженням;
- **нестабільні екрани** і «блимання»: екран відрізнявся, а наступний прогін знову збігся з тим самим еталоном, тобто «стрибає» екран, а не застосунок;
- **доступність:** найгірші екрани й найчастіші проблеми;
- **шум:** дрібні зміни, які раз у раз приймають;
- **знімання під час завантаження** і приховані зміни;
- **покриття:** яких перевірок бракує на кожному пристрої;
- **черга рев'ю:** скільки прогонів чекає на рішення і медіанний час до рішення.

Якщо проєкт зберігає не всю історію (ліміт збірок видалив старі), сторінка попереджає і
вважає «невикористаними» відносно того, що залишилося. Видалення у Vision не зачіпає
прод: це копія.

## 7. SDK: jar і pom.xml

SDK Vision — `ua.vision:vision-sdk`, версія `1.0.0`. Потрібен для надсилання XML-дерева екрана
(доступність, зміни й правила за елементами) і назви фічі в багах із порівняння. Працює на
Java 11+. Jar збирається з вихідного коду: `./scripts/build-sdk-jar.sh` (JDK 11, Gradle 7) кладе
`dist/sdk-java/vision-sdk-1.0.0.jar` і його pom; у репозиторії готового jar немає.

Класи `Vision`, `VisionConfig`, `VisionOptions`, `VisionResult` у пакеті `ua.vision.sdk`.
Налаштування — змінні `VISION_*` або файл `vision.json`. Дерево, більше за 10 МБ, SDK не надсилає:
пише попередження в лог, скриншот іде як звичайно (сервер такого дерева однаково не прийняв би).

### Перехід з 4.3.1-vision.N на 1.0.0

Старого пакета, змінних `VRT_*` і файлу `vrt.json` новий SDK не знає: тест на старих назвах
падає під час старту з повідомленням, якого налаштування бракує. Запити до сервера ті самі, еталони
залишаються. У тестовому проєкті:

1. Залежність: `com.github.Visual-Regression-Tracker:sdk-java:4.3.1-vision.N` →
   `ua.vision:vision-sdk:1.0.0` (варіант А або Б нижче); старий jar видалити.
2. Імпорти: `io.visual_regression_tracker.sdk_java.` → `ua.vision.sdk.` (заміна по всьому проєкту).
3. Змінні в CI: `VRT_APIURL`, `VRT_APIKEY`, `VRT_PROJECT`, `VRT_BRANCHNAME`… →
   `VISION_APIURL`, `VISION_APIKEY`, `VISION_PROJECT`, `VISION_BRANCHNAME`…
4. Файл `vrt.json`, якщо є, перейменувати на `vision.json` (вміст той самий).

З версій до `4.3.1-vision.4` ще й назви класів: `VisualRegressionTracker` → `Vision`,
`VisualRegressionTrackerConfig` → `VisionConfig`, `TestRunOptions` → `VisionOptions`,
`TestRunResult` → `VisionResult`.

```java
// було
import io.visual_regression_tracker.sdk_java.Vision;
// стало
import ua.vision.sdk.Vision;
```

### Варіант А: установити в локальний Maven (рекомендую)

Один раз на кожній машині, де збираються тести (ноутбук, агенти CI):

```bash
mvn install:install-file -Dfile=dist/sdk-java/vision-sdk-1.0.0.jar -DpomFile=dist/sdk-java/vision-sdk-1.0.0.pom
```

```xml
<dependency>
    <groupId>ua.vision</groupId>
    <artifactId>vision-sdk</artifactId>
    <version>1.0.0</version>
</dependency>
```

Залежності SDK (gson, slf4j) підтягнуться самі з pom, який установився разом із jar.

### Варіант Б: jar усередині проєкту тестів

Покласти jar у `libs/` проєкту тестів і закомітити. Тоді нічого встановлювати не треба:

```xml
<dependency>
    <groupId>ua.vision</groupId>
    <artifactId>vision-sdk</artifactId>
    <version>1.0.0</version>
    <scope>system</scope>
    <systemPath>${project.basedir}/libs/vision-sdk-1.0.0.jar</systemPath>
</dependency>
<!-- jar із файлу не приносить своїх залежностей; якщо вони вже є в проєкті, ці дві не потрібні -->
<dependency>
    <groupId>com.google.code.gson</groupId>
    <artifactId>gson</artifactId>
    <version>2.9.0</version>
</dependency>
<dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-api</artifactId>
    <version>1.7.25</version>
</dependency>
```

Maven попередить про `system` scope, це нормально.

`1.0.0` покрита тестами SDK (`gradle test`) і контрольним сценарієм (`./scripts/control-scenario.sh`:
справжній SDK проти справжнього сервера). У зовнішньому Maven-проєкті її ще не проганяли.
Публікацію в Nexus налаштовано (`gradle publish -PrepoUrl=...`, див. `sdk-java/README.md`).

### 7.1. Веб: Selenide

Той самий jar. Дерево сторінки збирає `ua.vision.sdk.web.WebUiTree` — одним викликом перед
скриншотом, у тому самому браузері (специфікація 050):

```java
String tree = WebUiTree.collect((JavascriptExecutor) WebDriverRunner.getWebDriver());
vision.track(name, screenshotBase64, VisionOptions.builder()
    .browser("chrome").browserVersion(version).viewport("1280x720")
    .uiTree(tree).featureName("Checkout").build());
```

Selenium SDK не тягне (`compileOnly`): він уже є в проєкті із Selenide. Якщо скрипт не
виконався (сторінку закрито, скрипт заборонено), `collect` повертає `null` і пише
попередження — скриншот іде без дерева, тест не падає. Звичайний `getPageSource()` теж
приймається, але без координат: лише невидимі зміни й перевірки доступності без контрасту
та області натискання.

### 7.2. Веб: Playwright

SDK для Playwright — `@vision/sdk-playwright` (порт `agent-playwright` VRT). Збирається з
вихідного коду, в npm не публікується:

```bash
cd sdk-playwright && npm ci && npm run build && npm pack   # → vision-sdk-playwright-1.0.0.tgz
```

У тестовому проєкті: `npm install --save-dev /шлях/до/vision-sdk-playwright-1.0.0.tgz`, потім
`@visual-regression-tracker/agent-playwright` → `@vision/sdk-playwright`,
`PlaywrightVisualRegressionTracker` → `VisionPlaywright`, змінні `VRT_*` → `VISION_*`
(`vrt.json` → `vision.json`). Запити до сервера ті самі, еталони залишаються; дерево сторінки,
версія браузера і `featureName` ідуть разом зі скриншотом. Докладно — `sdk-playwright/README.md`.

У проєкті Vision у налаштуваннях вибрати платформу «Веб» (або «Мобільний і веб»), якщо потрібно —
список дозволених браузерів у розділі «Пристрої».

## 8. Підключення автотестів

### 8.1. Куди надсилати

Адреса й ключ задаються змінними оточення, код для цього змінювати не треба:

```bash
export VISION_APIURL=http://vision-host:14200
```

```bash
export VISION_APIKEY=ваш_API_ключ
```

`VISION_PROJECT` і `VISION_BRANCHNAME` — як зараз (раніше `VRT_PROJECT` і `VRT_BRANCHNAME`). Ключ той самий, що на проді: його скопійовано.

Змінні працюють, лише якщо адресу й ключ **не задано в коді**. SDK бере значення з
`VisionConfig.builder().apiUrl(...)`, якщо воно там є, потім зі
змінної `VISION_APIURL`, потім із `vision.json`. Якщо в коді стоїть `.apiUrl("http://vrt-prod...")`,
винесіть його в змінну або системну властивість, наприклад
`.apiUrl(System.getenv().getOrDefault("VISION_APIURL", "http://vrt-prod:4200"))`.

Робочий прогін не чіпайте. Для Vision зробіть **окрему джобу**: той самий набір тестів із
цими двома змінними. Прод і далі отримуватиме свої прогони, Vision отримуватиме свої.

### 8.2. Додати XML екрана

Java:

```java
vision.track(
    "Payment",
    screenshotBase64,
    VisionOptions.builder()
        .device("Pixel 7 emulator")
        .os("Android 15")
        .uiTree(WebDriverRunner.getWebDriver().getPageSource())
        .featureName("Checkout")   // необов'язково: фіча для назви бага
        .build()
);
```

Kotlin:

```kotlin
vision.track(
    "Payment",
    screenshotBase64,
    VisionOptions.builder()
        .device("Pixel 7 emulator")
        .os("Android 15")
        .uiTree(WebDriverRunner.getWebDriver().pageSource)
        .featureName("Checkout")   // необов'язково: фіча для назви бага
        .build()
)
```

Якщо у вас обгортка над `vision.track`, правка одна, у ній. Без `.uiTree(...)` усе працює як
раніше. `featureName` потрапляє в назву бага з порівняння (`[Automation] [Checkout] …`); без нього
Vision бере частину назви перевірки до першої крапки. Еталони від нього не залежать.

### 8.3. Правила, про які варто пам'ятати

- **Назва перевірки** — головний ключ. Стани екрана — окремі перевірки:
  `Payment`, `Payment – error`, `Payment – bottom sheet`.
- **device і os** задають еталон пристрою. Передавайте їх стабільно, як зараз: емулятор
  і пристрій із BrowserStack — різні еталони однієї перевірки.
- **iOS і Android** — різні проєкти, як у вас зараз. Еталонний пристрій вибирається в
  кожному проєкті окремо.
- **Новий пристрій** приходить зі статусом «new»: прийміть його один раз, і в нього з'явиться
  свій еталон.

### 8.4. Дозволені пристрої

Щоб еталони не з'являлися для емуляторів, на яких CI не ганяється, у налаштуваннях проєкту є
розділ **Devices**: список «пристрій + версія OS». Поки він порожній, приймаються знімки з будь-якого
пристрою. Щойно в ньому є хоч один запис, знімок із SDK з іншого пристрою або іншої
версії OS відхиляється, і `track` падає (навіть із soft assert):

```
TestRunException: {"path":"/test-runs","name":"UnprocessableEntityException","message":"Device not allowed in project \"AOS\": check \"Payment\" was sent from device \"Pixel 6\", OS \"Android 13\". Allowed: \"Pixel 7 emulator\" / \"Android 15\". Run on an allowed device or add it in Project settings > Devices.", ...}
```

Порядок увімкнення:

1. Відкрийте **Settings → Devices**. Під списком — «Devices from snapshots»: пристрої саме в тому
   вигляді, у якому їх уже надсилають тести. Спершу додайте кнопкою **Add** ті, на яких ганяється
   CI, — інакше впаде весь прогін.
2. Для BrowserStack, який сам вибирає мінорну версію, вкажіть `26.*`: підійдуть `26`, `26.1`,
   `26.2.1`, але не `27.0`. `*` в іншому місці не збережеться.
3. Регістр і пробіли по краях не важливі. Ручні перевірки з CLI і MCP список не обмежує.

## 9. Ручні перевірки

У Vision: меню «?» → **Manual checks (CLI)**. Там три готові команди з ключем користувача:

```bash
curl -fsSLO http://vision-host:18080/cli/vision.py
```

```bash
python3 vision.py config --api http://vision-host:14200 --key КЛЮЧ --project "Mobile app"
```

```bash
python3 vision.py check "Payment"
```

- **Джерела екрана:**
  - під'єднаний Android-пристрій або емулятор (adb);
  - `--appium http://127.0.0.1:4723` — Appium-сесія, Android або iOS;
  - `--simulator` — iOS-симулятор, лише скриншот;
  - `--png файл.png --xml файл.xml` — готові файли.
- **Кілька екранів в одну збірку:** `start` / `finish`.
- **Гілка:** перевірки йдуть у гілку `manual` і порівнюються з еталонами основної гілки.
- **Еталони автотестів:** щоб порівнювати з ними попіксельно, додайте в `config`
  `--device` і `--os`, названі так само, як в автотестах.
- **Права:** для надсилання потрібна роль editor або admin.
- **Оточення:** Python 3.8+, без пакетів.
- **Для AI-асистентів** — MCP: `python3 vision.py mcp`.

не завантажується):


### Перехід на версію 1.0 (з версії до 1.0.0 SDK)

Нова версія шифрує секрети, захищає знімки підписом і розділяє проєкти за доступом
([042](docs/specs/042-project-access/spec.md)–[044](docs/specs/044-secrets-at-rest/spec.md)), тому
перехід — за кроками, а не одним `git pull`. Прод VRT при цьому лише читається.
Та сама інструкція окремим документом, з тим, що саме читається з VRT, — [upgrade-to-1.0](docs/guides/upgrade-to-1.0.md).

1. Зупинити старий Vision: `./scripts/vision.sh stop`.
2. Забрати код: `git pull`.
3. Перенести налаштування (покаже зміни, спитає `yes`, старий файл збереже поруч):

   ```bash
   python3 -I scripts/vision-convert-env.py --jira-hosts jira.example.com
   ```

   З'являться `VISION_SECRET_KEY` (зберігайте його: без нього токени Jira не прочитати), `VISION_JIRA_HOSTS`,
   новий `JWT_SECRET`; `POSTGRES_DB` залишиться попередньою базою.
4. Зібрати образи: `./scripts/vision.sh build`; один раз повернути собі файли `demo-data` (команда `chown`
   вище).
5. Свіжа копія проду, як завжди: `./scripts/demo-clone-from-prod.sh`.
6. Запустити: `./scripts/vision.sh up -d`. Під час першого старту застосуються міграції, усі отримають доступ
   до всіх проєктів, токени зашифруються, API-ключі з копії VRT перестануть працювати.
7. Перевірити (лише читання, звірка з VRT):

   ```bash
   ./scripts/vision-check-cutover.sh
   ```

8. Кожен створює новий API-ключ у профілі й прописує його в CI; тестові проєкти — на jar SDK
   1.0.0 (розділ 7).

**Відкат:** `./scripts/vision.sh stop`, `git checkout` попереднього коміту, старий `.env.demo` зі
збереженої копії (`.env.demo.before-vision-…`), `./scripts/demo-clone-from-prod.sh`,
`./scripts/vision.sh up -d --build`. Прод не змінювався, тому відкат — та сама копія.

## 12. Бекапи

Щоночі база Vision і нові картинки йдуть у папку `vision-backups` на «Моєму диску» Google
Drive робочого акаунта адміністратора ([013](docs/specs/013-backups-and-secrets/spec.md),
[017](docs/specs/017-backup-settings-ui/spec.md)). Бекап не шифрується, тому в ньому **немає
паролів, токенів Jira і ключів Gemini**; API-ключі є лише хешами, щоб автотести після
відновлення працювали без змін. Vision бачить на цьому Drive лише файли, які створив сам.

Потрібен доступ сервера до `oauth2.googleapis.com`, `www.googleapis.com` і Docker Hub. rclone
ставити не треба: скрипти запускають Docker-образ `rclone/rclone:1.68.2`, якщо rclone немає на
сервері.

### Налаштувати один раз

1. **OAuth-клієнт** у [Google Cloud Console](https://console.cloud.google.com), у проєкті вашої організації
   (докладно, з помилками й чому так — [google-drive-access](docs/guides/google-drive-access.md)):
   - «APIs & Services» → «Library» → **Google Drive API** → «Enable»;
   - «OAuth consent screen» (або «Google Auth Platform») → тип **Internal**, назва `Vision
     backups`. Якщо Internal недоступний, проєкт створено поза вашою організацією: створіть його в ній.
     У типу External у режимі Testing доступ зникає через 7 днів;
   - «Credentials» → «Create credentials» → «OAuth client ID» → тип **TVs and Limited Input
     devices** → «Create». Збережіть Client ID і Client secret.
2. **`.env.demo`** — майстер-логін для входу після відновлення:

   ```bash
   VISION_MASTER_EMAIL=ваш_email
   VISION_MASTER_PASSWORD=не_коротше_12_символів
   ```

   Збережіть їхню копію **поза** сервером: на новій машині їх доведеться ввести знову.
3. **Оновити Vision і поставити розклад:**

   ```bash
   ./scripts/vision.sh up -d --build
   ```

   ```bash
   ./scripts/vision-backup.sh --install-cron
   ```

   cron раз на 5 хвилин перевіряє, чи не час робити бекап і чи не просили його на сторінці Backups.
   Журнал — `demo-data/backups/cron.log`. Користувачу, який ставить cron, потрібен доступ до `docker`.
4. **У Vision** під адміністратором: меню акаунта → **Backups** → «Google Drive» → вставити
   Client ID і Client secret → «Connect» → відкрити показане посилання (google.com/device) на будь-якому
   пристрої, увійти робочим акаунтом, ввести код і дозволити доступ. Сторінка покаже
   «Connected as …».
5. На тій самій сторінці: «Test connection», за бажанням час і кількість копій у «Schedule», потім
   **«Back up now»**. Протягом 5 хвилин бекап з'явиться у списку «In Google Drive».

На Drive зберігаються останні дампи бази (7, змінюється в «Schedule») і картинки, потрібні хоча б
одному з них: нові довантажуються, а картинка видаленого у Vision еталона зникає з Drive разом з
останнім дампом, де вона ще була (приблизно через тиждень). Локальні картинки не чіпаються. Якщо Drive недоступний, бекап залишається в `demo-data/backups` і йде під час наступного
запуску. Якщо останньому успішному бекапу більше ніж 26 годин, адміністратори бачать попередження
з посиланням на сторінку Backups. `demo-clone-from-prod.sh` сам робить бекап перед тим, як
замінити непорожню базу Vision.

Без інтерфейсу можна й по-старому: `BACKUP_REMOTE=назва_remote:папка` в `.env.demo` і конфіг rclone у
`RCLONE_CONFIG_DIR` (за замовчуванням `~/.config/rclone`). Підключення на сторінці Backups має пріоритет.

### Відновити

```bash
./scripts/vision-restore.sh
```

Бере останній бекап (або вказаний: `./scripts/vision-restore.sh vision-20261027T031700Z.tar`),
показує план і чекає `yes`. На чистій машині: §2–3 (код і `.env.demo`), кроки 1–3 вище, увійти
користувачем за замовчуванням порожнього Vision (`DEFAULT_USER_EMAIL` / `DEFAULT_USER_PASSWORD` з
`.env.demo`; email типово `admin@vision.local`, пароль типового немає), підключити Drive
на сторінці Backups тим самим робочим акаунтом і тим самим OAuth-клієнтом (Vision бачить лише файли
свого клієнта), потім restore:
підключення лежить у `demo-data/backup-config` і відновленням бази не затирається.

Після відновлення:
- входьте майстер-логіном; він стає адміністратором;
- іншим користувачам задайте пароль: Users → виділити користувача → «Set password»;
- токени Jira і ключі Gemini кожен вводить заново в профілі;
- API-ключі й автотести — без змін.

## 13. Якщо щось пішло не так

| Симптом | Що робити |
|---|---|
| «containers that were not created from …» | у проєкті `vision` є чужі контейнери. Скрипт нічого не зробив. З'ясуйте, чиї вони (`docker ps -a --filter label=com.docker.compose.project=vision`), не видаляйте наосліп |
| «Not enough disk …» | звільніть місце (`docker system df`, `docker builder prune`) або, для картинок, `PROD_IMAGES_MODE=link` |
| «production VRT is older than 5.x» | спершу оновіть прод або запускайте Vision на порожній базі (без кроку 4) |
| «Production has migrations Vision does not know» | схема проду новіша за Vision: потрібна міграція у Vision під неї |
| `migration` у стані Exited (1) | `./scripts/vision.sh logs migration` |
| `docker-credential-desktop: executable file not found` | на macOS `vision.sh` сам додає в `PATH` папку Docker Desktop (`/Applications/Docker.app/Contents/Resources/bin`); якщо Docker стоїть в іншому місці, вкажіть її у `VISION_DOCKER_APP_BIN` |
| Збирання `up -d --build` триває багато хвилин без виводу | вибрано збирач в окремому контейнері (`docker buildx ls`, зірочка біля `docker-container`): `vision.sh` сам збирає вбудованим збирачем Docker і пише про це; свій збирач — через `BUILDX_BUILDER` |
| Не працює вхід | `DEMO_API_URL` має відкриватися з браузера; `./scripts/vision.sh logs api` |
| У старих прогонів немає картинок | `PROD_IMAGES_DIR` вказував не туди: виправити й повторити крок 4 |
| Прод зберігає картинки в S3 | скопіюйте бакет в **окремий** бакет і вкажіть його API Vision тими самими змінними `AWS_*`, що й у проду. Бакет проду Vision вказувати не можна: Vision видаляє старі картинки |

## 14. Видалення

```bash
./scripts/vision.sh down
```

```bash
rm -rf demo-data
```

Прод це не зачіпає, і в режимі `link` теж: видаляється посилання, файл проду залишається.
