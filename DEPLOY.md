# Vision: развёртывание и подключение тестов

Vision ставится на ту же машину, что и рабочий VRT, и работает на **копии** его базы и картинок.
Рабочий VRT продолжает работать как раньше; автотесты переключаются на Vision отдельным запуском,
когда вы решите.

## 0. Безопасность рабочего сервера

Что Vision делает с продом: **только читает**.

| Что | Как | Почему безопасно |
|---|---|---|
| База прода | `pg_dump` внутри контейнера прода (или по строке подключения) | pg_dump работает в транзакции только для чтения; запускается с наименьшим приоритетом CPU (`nice 19`) |
| Проверки перед копированием | несколько `SELECT`: имя и размер базы, есть ли таблицы VRT, список проектов, число пользователей | только чтение |
| Картинки прода | копирование (по умолчанию) или жёсткие ссылки (`PROD_IMAGES_MODE=link`) | файлы прода не открываются на запись. Vision пишет только новые файлы со случайными именами и никогда в существующие; удаление в Vision убирает только его копию или ссылку |

Что защищает от ошибок:
- **Все команды compose идут только через `./scripts/vision.sh`.** Имя проекта зашито (`vision`)
  и не берётся из `COMPOSE_PROJECT_NAME`, даже если она выставлена в shell.
- **Перед любой командой** скрипты проверяют, что все контейнеры проекта `vision` созданы из
  `docker-compose.demo.yml` этого репозитория. Если найден чужой контейнер (например, прод
  когда-то запущен с тем же именем проекта), не делается **ничего**.
- **Очистка базы** при копировании выполняется только в контейнере, который проверен как
  собственный Postgres Vision. Скрипт отказывается работать, если `PROD_PG_CONTAINER` указывает
  на контейнер Vision, а `PROD_IMAGES_DIR` — на папку Vision.
- **Диск.** Перед копированием и сборкой скрипты проверяют, что после операции останется не
  меньше 10 ГБ или 5% диска, что больше (`VISION_DISK_RESERVE_GB`). Если нет, ничего не
  делается: заполненный диск — главный способ навредить проду, стоящему рядом.
- **CPU и память Vision ограничены:** API — 2 CPU и 3 ГБ, сравнение картинок в 2 потока,
  Postgres — 1 CPU и 1 ГБ, UI — 0.5 CPU (настраивается в `.env.demo`).
- **Перед копированием** скрипт показывает, что прочитает и что заменит, и ждёт `yes`.

Проверено на стенде с upstream VRT 5.6.3 на postgres:12. Сняли «отпечаток» прода (хеши
содержимого всех таблиц, хеши всех картинок, время запуска контейнеров) до и после:
- отказов защиты (чужой проект `vision`, чужая `COMPOSE_PROJECT_NAME`);
- двух копирований (копия и ссылки);
- сборки и запуска;
- проверок из SDK и CLI;
- приёма прогонов и удаления сборок в Vision.

Отпечатки совпали полностью.

Что остаётся на вас:
- **Сборка образов** (шаг 5) несколько минут грузит CPU машины. Делайте её, когда прод не под
  пиковой нагрузкой.
- **pg_dump** большой базы держит долгую читающую транзакцию. Для VRT это безопасно, но лучше
  запускать копирование не в пик.
- **В режиме `link`** файлы, которые прод удалит при своей очистке, продолжают занимать место,
  пока на них ссылается Vision. Скрипт копирования можно запускать заново, чтобы обновить данные.
- **Никогда не указывайте** в `DEMO_*` и `POSTGRES_*` порты, базу или папки прода.

## 1. Что нужно

- Docker с Compose v2 (`docker compose version`), git, bash, rsync.
- Место на диске: около 6 ГБ под образы, плюс 2× размер базы, плюс размер картинок (в режиме
  `copy`). Скрипты посчитают сами.
- Свободные порты: 18080 (UI), 14200 (API), 15432 (Postgres, только localhost). Меняются в
  `.env.demo`.
- Имя Docker-контейнера с базой прода (`docker ps`) или строка подключения к ней.
- Папка картинок прода: то, что смонтировано в его API как `/imageUploads`. Если прод хранит
  картинки в S3, см. раздел 12.

Прод должен быть VRT 5.x и не новее форка. Скрипт проверит это сам.

## 3. Настройка

```bash
cp .env.demo.example .env.demo
```

Заполнить в `.env.demo`:

| Переменная | Что указать |
|---|---|
| `JWT_SECRET` | любой длинный секрет (можно тот же, что у прода: тогда у пользователей работают выданные токены входа) |
| `DEMO_UI_URL` | адрес UI так, как его видит браузер, например `http://vision-host:18080` |
| `DEMO_API_URL` | адрес API так, как его видит браузер и автотесты, например `http://vision-host:14200` |
| `PROD_PG_CONTAINER` | имя контейнера Postgres прода, **или** |
| `PROD_DATABASE_URL` | строка подключения к базе прода |
| `PROD_DB_NAME` | имя базы VRT в этом контейнере, если это не его `POSTGRES_DB`. Смотрите `DATABASE_URL` API прода: имя базы — после последнего `/`. Пусто — `POSTGRES_DB` |
| `PROD_IMAGES_DIR` | папка картинок прода |
| `PROD_IMAGES_MODE` | `copy` (по умолчанию) или `link` (без лишнего места, тот же диск) |

## 4. Копия данных прода

```bash
./scripts/demo-clone-from-prod.sh
```

Копируется **вся база VRT**: все проекты (iOS, Android и остальные), сборки, эталоны,
история, пользователи с паролями, API-ключи, настройки проектов. Перед подтверждением скрипт
показывает список проектов прода с числом сборок и эталонов, например:

```
  read from production:  database "vrt" (container vrt-postgres-1, 2.1 GB), read-only, all of it:
                         3 projects, 12 users
                           - Android app  (412 builds, 960 baselines)
                           - iOS app  (388 builds, 870 baselines)
                           - Web  (95 builds, 120 baselines)
```

Если выбранная база не содержит таблиц VRT (например, в том же Postgres живут другие
приложения, а `POSTGRES_DB` указывает не на VRT), скрипт остановится и покажет список баз на
сервере. Тогда укажите нужную в `PROD_DB_NAME`. После копирования скрипт сверяет число
проектов и пользователей в копии и в проде.

Скрипт покажет план и спросит `yes`. Дальше:
1. проверит место на диске и чужие контейнеры;
2. сделает `pg_dump` прода (только чтение) и восстановит дамп в Postgres Vision;
3. проверит, что прод — VRT 5.x и не новее форка;
4. скопирует или свяжет картинки.

Запускать можно повторно, чтобы взять свежие данные: всё, что сделано в Vision, заменится
текущим состоянием прода.

## 5. Запуск и проверка

```bash
./scripts/vision.sh up -d --build
```

```bash
./scripts/vision.sh ps -a
```

Должно быть: `migration` — **Exited (0)**, а `api`, `ui` и `postgres` — **Up**.

```bash
curl -s http://localhost:14200/health
```

Ответ `{"status":"ok",...}`. В логе миграций в конце должно быть `All migrations have been
successfully applied`:

```bash
./scripts/vision.sh logs migration
```

Открыть `DEMO_UI_URL` и войти **продовой** учёткой. Пользователи, пароли, проекты, сборки и
API-ключи скопированы.

## 6. Настройки в Vision

Projects → карандаш у проекта:
- **Mobile screenshots → Reference device**: устройство, с которым справочно сравниваются
  остальные, например эмулятор. На статусы это не влияет.
- **Jira**: URL и токен (для Jira Cloud ещё email). Тогда из ревью можно заводить баги по
  доступности.

## 7. SDK: jar и pom.xml

**Пока ничего менять не нужно.** Vision понимает текущий SDK как есть: скриншоты, статусы, группы
изменений работают. Новый SDK нужен только для отправки XML-дерева экрана: доступность,
изменения по элементам, правила по элементам.

Новый SDK — это upstream 4.3.1 плюс одно необязательное поле `uiTree`. Пакет и классы те же,
работает на Java 11+. Готовый jar лежит в репозитории: `dist/sdk-java/sdk-java-4.3.1-vision.1.jar`
(рядом его pom). Пересобрать: `./scripts/build-sdk-jar.sh` (JDK 11–17, Gradle 7).

### Вариант А: установить в локальный Maven (рекомендую)

Один раз на каждой машине, где собираются тесты (ноутбук, агенты CI):

```bash
mvn install:install-file -Dfile=dist/sdk-java/sdk-java-4.3.1-vision.1.jar -DpomFile=dist/sdk-java/sdk-java-4.3.1-vision.1.pom
```

В pom.xml меняется только версия:

```xml
<dependency>
    <groupId>com.github.Visual-Regression-Tracker</groupId>
    <artifactId>sdk-java</artifactId>
    <version>4.3.1-vision.1</version>
</dependency>
```

Зависимости SDK (gson, slf4j) подтянутся сами из pom, который установился вместе с jar.

### Вариант Б: jar внутри проекта тестов

Положить jar в `libs/` проекта тестов и закоммитить. Тогда ничего устанавливать не нужно:

```xml
<dependency>
    <groupId>com.github.Visual-Regression-Tracker</groupId>
    <artifactId>sdk-java</artifactId>
    <version>4.3.1-vision.1</version>
    <scope>system</scope>
    <systemPath>${project.basedir}/libs/sdk-java-4.3.1-vision.1.jar</systemPath>
</dependency>
<!-- jar из файла не приносит своих зависимостей; если они уже есть в проекте, эти две не нужны -->
<dependency>
    <groupId>com.google.code.gson</groupId>
    <artifactId>gson</artifactId>
    <version>2.9.0</version>
</dependency>
<dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-api</artifactId>
    <version>1.7.25</version>
</dependency>
```

Maven предупредит о `system` scope, это нормально.

Оба варианта проверены Maven-проектом: собирается и отправляет экраны с XML в Vision.
Публикация в Nexus тоже настроена (`gradle publish -PrepoUrl=...`, см. `sdk-java/README.md`),
пригодится, когда захотите убрать ручной шаг.

## 8. Подключение автотестов

### 8.1. Куда отправлять

Адрес и ключ задаются переменными окружения, код для этого менять не нужно:

```bash
export VRT_APIURL=http://vision-host:14200
```

```bash
export VRT_APIKEY=ваш_API_ключ
```

`VRT_PROJECT` и `VRT_BRANCHNAME` — как сейчас. Ключ тот же, что на проде: он скопирован.

Переменные работают, только если адрес и ключ **не заданы в коде**. SDK берёт значение из
`VisualRegressionTrackerConfig.builder().apiUrl(...)`, если оно там есть, затем из
переменной `VRT_APIURL`, затем из `vrt.json`. Если в коде стоит `.apiUrl("http://vrt-prod...")`,
вынесите его в переменную или системное свойство, например
`.apiUrl(System.getenv().getOrDefault("VRT_APIURL", "http://vrt-prod:4200"))`.

Рабочий прогон не трогайте. Для Vision сделайте **отдельную джобу**: тот же набор тестов с
этими двумя переменными. Прод продолжит получать свои прогоны, Vision будет получать свои.

### 8.2. Добавить XML экрана

Java:

```java
vrt.track(
    "Payment",
    screenshotBase64,
    TestRunOptions.builder()
        .device("Pixel 7 emulator")
        .os("Android 15")
        .uiTree(WebDriverRunner.getWebDriver().getPageSource())
        .build()
);
```

Kotlin:

```kotlin
vrt.track(
    "Payment",
    screenshotBase64,
    TestRunOptions.builder()
        .device("Pixel 7 emulator")
        .os("Android 15")
        .uiTree(WebDriverRunner.getWebDriver().pageSource)
        .build()
)
```

Если у вас обёртка над `vrt.track`, правка одна, в ней. Без `.uiTree(...)` всё работает как
раньше.

### 8.3. Правила, о которых стоит помнить

- **Название проверки** — главный ключ. Состояния экрана — отдельные проверки:
  `Payment`, `Payment – error`, `Payment – bottom sheet`.
- **device и os** задают эталон устройства. Передавайте их стабильно, как сейчас: эмулятор
  и устройство из BrowserStack — разные эталоны одной проверки.
- **iOS и Android** — разные проекты, как у вас сейчас. Эталонное устройство выбирается в
  каждом проекте отдельно.
- **Новое устройство** приходит со статусом «new»: примите его один раз, и у него появится
  свой эталон.

## 9. Ручные проверки

В Vision: меню «?» → **Manual checks (CLI)**. Там три готовые команды с ключом пользователя:

```bash
curl -fsSLO http://vision-host:18080/cli/vision.py
```

```bash
python3 vision.py config --api http://vision-host:14200 --key КЛЮЧ --project "Mobile app"
```

```bash
python3 vision.py check "Payment"
```

- **Источники экрана:**
  - подключённое Android-устройство или эмулятор (adb);
  - `--appium http://127.0.0.1:4723` — Appium-сессия, Android или iOS;
  - `--simulator` — iOS-симулятор, только скриншот;
  - `--png файл.png --xml файл.xml` — готовые файлы.
- **Несколько экранов в одну сборку:** `start` / `finish`.
- **Ветка:** проверки идут в ветку `manual` и сравниваются с эталонами основной ветки.
- **Эталоны автотестов:** чтобы сравнивать с ними попиксельно, добавьте в `config`
  `--device` и `--os`, названные так же, как в автотестах.
- **Права:** для отправки нужна роль editor или admin.
- **Окружение:** Python 3.8+, без пакетов.
- **Для AI-ассистентов** — MCP: `python3 vision.py mcp`.

## 12. Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| «containers that were not created from …» | в проекте `vision` есть чужие контейнеры. Скрипт ничего не сделал. Выясните, чьи они (`docker ps -a --filter label=com.docker.compose.project=vision`), не удаляйте вслепую |
| «Not enough disk …» | освободите место (`docker system df`, `docker builder prune`) или, для картинок, `PROD_IMAGES_MODE=link` |
| «production VRT is older than 5.x» | сначала обновите прод, или запускайте Vision на пустой базе (без шага 4) |
| «Production has migrations this fork does not know» | прод новее форка: нужно подтянуть upstream в форк |
| `migration` в состоянии Exited (1) | `./scripts/vision.sh logs migration` |
| Не работает вход | `DEMO_API_URL` должен открываться из браузера; `./scripts/vision.sh logs api` |
| У старых прогонов нет картинок | `PROD_IMAGES_DIR` указывал не туда: исправить и повторить шаг 4 |
| Прод хранит картинки в S3 | скопируйте бакет в **отдельный** бакет и укажите его API Vision теми же переменными `AWS_*`, что у прода. Бакет прода Vision указывать нельзя: Vision удаляет старые картинки |

## 13. Удаление

```bash
./scripts/vision.sh down
```

```bash
rm -rf demo-data
```

Прод это не затрагивает, и в режиме `link` тоже: удаляется ссылка, файл прода остаётся.
