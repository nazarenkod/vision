# ADR-0001: Форк як монорепозиторій із git subtree

| | |
|---|---|
| Статус | Accepted |
| Дата | 2026-10-24 |
| Хто вирішив | Дмитро Назаренко |

## Контекст

Upstream VRT — це три окремі репозиторії: backend, frontend і sdk-java. Фічі Vision одночасно
зачіпають усі три (поле в SDK, обробка на бекенді, UI), а оновлення з upstream мають лишатися
можливими.

## Чинники рішення

- Одна зміна мусить охоплювати всі шари й перевірятися разом.
- Оновлення з upstream мають лишатися можливими.
- Один репозиторій для розгортання на сервері.

## Розглянуті варіанти

1. Три окремі форки
2. Монорепозиторій, `git subtree add --squash`
3. Git submodules

## Рішення

Монорепозиторій `vision` з папками `backend/`, `frontend/`, `sdk-java/`, імпортованими
`git subtree add --squash` з upstream master. Робоча гілка `mvp/demo` пушиться у `vision/main`.
Remote `origin` — upstream, туди не пушимо.

## Наслідки

- Добре: одна зміна — один коміт, одна перевірка.
- Погано: конфлікти при `subtree pull` там, де змінено код upstream. Тому такі зміни робимо мінімальними й локалізованими.

## Як перевіряємо

Hook агента блокує `git push` не в `vision` (`.claude/hooks/guard.py`); `git log --oneline -- backend` показує коміти імпорту.

## Варіанти: за і проти

### 1. Три окремі форки

- Добре: звичний upstream-процес.
- Погано: зміна фічі — три PR, які треба синхронізувати; розгортання з трьох репозиторіїв.

### 2. Монорепозиторій, `git subtree add --squash`

- Добре: атомарні зміни; `git subtree pull --squash` по кожній папці.
- Погано: історію upstream стиснуто в один коміт на імпорт.

### 3. Git submodules

- Добре: історія upstream ціла.
- Погано: зміни у форках сабмодулів однаково потрібні; складніше для людей і агентів.
