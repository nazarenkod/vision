# ADR-0003: Лише додавальні зміни схеми

| | |
|---|---|
| Статус | Accepted |
| Дата | 2026-10-24 |
| Хто вирішив | Дмитро Назаренко |

## Контекст

Vision працює на копії бази upstream VRT, а згодом може працювати на живій базі або поруч із
новими версіями upstream.

## Чинники рішення

- Upstream має працювати на базі після міграцій Vision.
- Відкат Vision не повинен ламати дані.

## Розглянуті варіанти

1. Вільні міграції
2. Лише додавальні: нові таблиці, nullable-колонки, індекси
3. Окрема база для даних Vision

## Рішення

Друга опція. Без змін enum, видалень, перейменувань, `NOT NULL` на наявних колонках і
перетворення даних у міграції. Перенесення старих даних, якщо потрібне, робить застосунок при
старті, і воно ідемпотентне (приклад — `moveIssueStates`).

## Наслідки

- Добре: upstream VRT може працювати на базі після міграцій Vision.
- Погано: старі таблиці (`A11yIssueState`) лишаються, доки дані не перенесено.

## Як перевіряємо

`/verify` шукає в нових міграціях `DROP`, `RENAME`, `ALTER TYPE`, `SET NOT NULL`.

## Варіанти: за і проти

### 1. Вільні міграції

- Добре: простіша модель.
- Погано: upstream і відкат ламаються.

### 2. Лише додавальні: нові таблиці, nullable-колонки, індекси

- Добре: сумісність в обидва боки.
- Погано: старі формати живуть поруч із новими.

### 3. Окрема база для даних Vision

- Добре: повна ізоляція.
- Погано: зв'язки між базами, дві міграційні системи.
