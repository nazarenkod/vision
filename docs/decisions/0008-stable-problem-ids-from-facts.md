# ADR-0008: Стабільні ID проблем; ідентичність — з фактів

| | |
|---|---|
| Статус | Accepted |
| Дата | 2026-10-26 |
| Хто вирішив | Дмитро Назаренко |

## Контекст

Перша версія обчислювала ID проблеми з ключа, а ключ залежав від налаштувань (режим дублів,
класи). Зміна налаштувань змінювала ID і відривала заведені баги. Команда хоче гнучко
налаштовувати групування і робити це без втрат.

## Чинники рішення

- ID не змінюється ніколи.
- Налаштування можна міняти будь-коли.
- Немає ручних міграцій.

## Розглянуті варіанти

1. ID = хеш ключа за поточними налаштуваннями
2. ID при створенні + факти місць; ключ перераховується щоразу
3. Таблиця відповідностей старих і нових ID при зміні налаштувань

## Рішення

Друга опція. Проблема зберігає ID і факти (правило, id елемента, компонент, екран, замір,
клас, підпис). `problemKeyOf(факти, налаштування)` обчислюється для знахідок і для фактів
збережених проблем; збіг ключа — та сама проблема.

## Наслідки

- Добре: склеєні налаштуваннями проблеми показують усі баги; розділені — тримають баг за кожною частиною.
- Погано: індекс проблем проєкту в пам'яті; Unlink частини розділеної проблеми прибирає лише цю частину фактів.

## Як перевіряємо

`a11y-issues.spec.ts › keeps ids and bugs of problems decided under another grouping`.

## Оновлення

[021](../specs/021-fixed-a11y-grouping/spec.md) прибрала налаштування групування: правило тепер
одне для всіх проєктів, і `problemKeyOf` бере лише факти. Рішення лишається чинним: проблеми,
вирішені за старими налаштуваннями, розкладаються за фактами й тримають ID і баги. Той самий
механізм знадобиться для поправок групування з картки в рев'ю.

## Варіанти: за і проти

### 1. ID = хеш ключа за поточними налаштуваннями

- Добре: просто, без зберігання.
- Погано: зміна налаштувань губить зв'язок з багами.

### 2. ID при створенні + факти місць; ключ перераховується щоразу

- Добре: ID стабільний, групування гнучке.
- Погано: індекс проблем на кожне рев'ю (кешується).

### 3. Таблиця відповідностей старих і нових ID при зміні налаштувань

- Добре: ID ніби стабільні.
- Погано: складна міграція при кожній зміні; помилки зіставлення.
