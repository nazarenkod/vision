# ADR-0010: Особисті токени Jira

| | |
|---|---|
| Статус | Accepted |
| Дата | 2026-10-26 |
| Хто вирішив | Дмитро Назаренко |

## Контекст

Зі спільним токеном проєкту всі баги заводились би від імені однієї людини, а права в Jira
були б однакові для всіх.

## Чинники рішення

- Справжній автор у Jira.
- Права людини, а не сервісного акаунта.
- Сумісність з уже налаштованим сервером.

## Розглянуті варіанти

1. Лише спільний токен проєкту
2. Особисті токени, спільний — як запасний
3. OAuth 2.0 (3LO) з Jira Cloud

## Рішення

Друга опція. Токен (і email для Cloud) — у профілі. Vision звертається до Jira від імені того,
хто діє; спільний токен — лише коли особистого немає. Токени лише записуються, API повертає
`jiraTokenSet`.

## Наслідки

- Добре: у Jira видно автора.
- Погано: пошук під час рев'ю залежить від токена того, хто дивиться; токени поки не зашифровані ([013](../specs/013-backups-and-secrets/spec.md)).

## Як перевіряємо

`a11y-problems.service.spec.ts › files as the person with their own token…`; історія еталонів віддає лише id, ім'я й email.

## Варіанти: за і проти

### 1. Лише спільний токен проєкту

- Добре: налаштувати раз.
- Погано: один автор, широкі права.

### 2. Особисті токени, спільний — як запасний

- Добре: справжній автор; працює й без особистого.
- Погано: кожен додає токен сам.

### 3. OAuth 2.0 (3LO) з Jira Cloud

- Добре: без ручних токенів.
- Погано: реєстрація застосунку в Atlassian, адміністратор, складніше для DC.
