# ADR-0013: Інтерфейс керує скриптами хоста через файли

| | |
|---|---|
| Статус | Accepted |
| Дата | 2026-10-27 |
| Хто вирішив | Дмитро Назаренко |

## Контекст

Бекапи налаштовують і запускають з інтерфейсу ([017](../specs/017-backup-settings-ui/spec.md)),
а роблять їх скрипти хоста: лише там є запобіжники `vision-safety.sh`, доступ до контейнера бази
й до зупинки API. Vision стоїть поруч із робочим VRT, тож API не повинен керувати Docker.

## Чинники рішення

- API не отримує влади над контейнерами хоста (ADR-0002).
- Мінімум рухомих частин; працює й без мережевих портів між API і хостом.
- Скрипти лишаються головними: їх можна запустити руками.

## Розглянуті варіанти

1. Змонтувати Docker socket в API й запускати скрипти звідти
2. Обмін файлами в спільній папці; cron на хості кожні 5 хвилин
3. Окремий агент на хості з HTTP API

## Рішення

Друга опція. API пише налаштування й запити в `demo-data/backup-config/`, скрипт хоста їх читає
й пише стан у `demo-data/backup-status/`. Файли віддаються користувачу хоста (`chown` на
`BACKUP_FILES_OWNER`), секрети — з правами `600`.

## Наслідки

- Добре: API не може зачепити контейнери проду; скрипт працює й без інтерфейсу.
- Погано: дія з інтерфейсу виконується із затримкою до 5 хвилин; треба один раз поставити cron.
- Нові дії інтерфейсу над хостом додаються тим самим способом: файл-запит + перевірка в cron.

## Як перевіряємо

`scripts/tests/test_vision_backup.py › test_runs_a_requested_backup_once`.

## Варіанти: за і проти

### 1. Змонтувати Docker socket в API й запускати скрипти звідти

- Добре: дія одразу.
- Погано: API отримує root на хості й доступ до контейнерів проду.

### 2. Обмін файлами в спільній папці; cron на хості кожні 5 хвилин

- Добре: безпечно, просто, скрипти незалежні.
- Погано: затримка до 5 хвилин; cron треба поставити.

### 3. Окремий агент на хості з HTTP API

- Добре: дія одразу, без cron.
- Погано: ще один сервіс, порт і автентифікація між ним і API.
