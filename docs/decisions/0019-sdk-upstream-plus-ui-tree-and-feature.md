# ADR-0019: SDK — upstream плюс UI-дерево й назва фічі

| | |
|---|---|
| Статус | Accepted |
| Дата | 2026-10-29 |
| Хто вирішив | Дмитро Назаренко |

## Контекст

[ADR-0004](0004-sdk-upstream-plus-ui-tree.md) дозволив у SDK одну зміну відносно upstream 4.3.1 —
необов'язковий `uiTree`. Баги з порівняння ([025](../specs/025-bug-from-comparison/spec.md))
називаються `[Automation] [фіча] суть`. Зараз фіча — частина назви перевірки до першої крапки, але
назви тестів не завжди так побудовані, і власник хоче передавати фічу з тесту явно.

Готове поле upstream `customTags` не підходить: воно входить в ідентичність перевірки й ключ
еталона ([ADR-0005](0005-check-by-name-baseline-per-device.md)), тож фіча в ньому створила б нові
еталони для всіх наявних перевірок.

## Чинники рішення

- Наявні тести не переписуються; без нового параметра запит такий самий, як зараз.
- Назва фічі не змінює ідентичності перевірки й не скидає еталонів.
- Перехід — заміна jar, як і для `uiTree`.

## Розглянуті варіанти

1. Новий необов'язковий параметр `featureName` поруч із `uiTree`
2. Фіча в `customTags`
3. Лише конвенція назви: фіча до першої крапки

## Рішення

Обрано варіант 1: SDK відрізняється від upstream 4.3.1 двома необов'язковими параметрами,
`uiTree` і `featureName`. Сервер зберігає фічу як підпис знімка поза ідентичністю перевірки; без неї
бере частину назви до першої крапки. Інших змін API SDK не робимо.

## Наслідки

- Добре: назва бага точна без перейменування тестів; еталони не скидаються.
- Добре: правило лишається жорстким — перелік дозволених змін явний.
- Погано: ще одне розходження з upstream і перевипуск jar (`4.3.1-vision.N+1`) для команд.

## Як перевіряємо

`git diff` `sdk-java/` проти upstream 4.3.1 містить лише `uiTree`, `featureName` і їхні тести; тест
сервера показує, що знімок з `featureName` і без неї порівнюється з тим самим еталоном.

## Варіанти: за і проти

### 1. Новий необов'язковий параметр `featureName`

- Добре: явно, не чіпає ідентичності перевірки.
- Погано: друга зміна SDK; сервер upstream має його ігнорувати.

### 2. Фіча в `customTags`

- Добре: без зміни SDK.
- Погано: `customTags` — частина ключа еталона; нові еталони для всіх перевірок.

### 3. Лише конвенція назви

- Добре: нічого не змінюємо.
- Погано: залежить від дисципліни назв; власник хоче явний параметр.
