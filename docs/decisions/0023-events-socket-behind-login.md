# ADR-0023: Сокет подій — лише з токеном входу і по кімнатах проєктів

| | |
|---|---|
| Статус | Proposed |
| Дата | 2026-11-01 |
| Хто вирішив | Дмитро Назаренко |

## Контекст

Шлюз socket.io з upstream VRT приймає будь-яке з'єднання й розсилає всім цілі рядки `Build` і
`TestRun` усіх проєктів, тоді як REST API вимагає токен входу або ключ API. Будь-хто, хто
дістається до адреси Vision, може слухати дані збірок наживо ([032](../specs/032-authenticated-events/spec.md)).

## Чинники рішення

- Той самий вхід, що й для API: окремої схеми автентифікації не заводимо.
- Зміни коду upstream мінімальні й локалізовані ([ADR-0001](0001-fork-as-subtree-monorepo.md)).
- Події лише вебінтерфейсу Vision; SDK, CLI і MCP їх не слухають.
- Працює з кількома екземплярами за `RedisIoAdapter`.

## Розглянуті варіанти

1. JWT на рукостисканні (`auth.token`) + кімнати проєктів
2. JWT на рукостисканні, розсилка всім, як була
3. Перевірка на кожну подію (токен у кожному повідомленні)
4. Прибрати сокет, інтерфейс опитує API

## Рішення

Обрано варіант 1. Middleware шлюзу перевіряє токен тим самим `JWT_SECRET`, що й `JwtStrategy`,
розриває з'єднання, коли спливає `exp`, а розсилка йде лише в кімнату проєкту, на який
підписалось з'єднання (`subscribe`). Ключ API сокет не відкриває.

## Наслідки

- Добре: без входу подій не отримати; кожен інтерфейс отримує лише свій проєкт.
- Добре: нова подія наживо мусить мати проєкт — інакше вона нікому не дійде; це видно одразу.
- Погано: клієнт upstream VRT без токена з сервером Vision подій не отримає.
- Погано: `git subtree pull` конфліктуватиме в `events.gateway.ts` і `socket.context.tsx`.

## Як перевіряємо

`backend/src/shared/events/events.gateway.spec.ts` піднімає справжній сервер socket.io і
перевіряє відмови, прийняття й кімнати клієнтом `socket.io-client`.

## Варіанти: за і проти

### 1. JWT на рукостисканні + кімнати

- Добре: одна перевірка на з'єднання; розсилка менша; стандартний механізм socket.io.
- Погано: клієнт має повідомляти, який проєкт відкритий.

### 2. JWT без кімнат

- Добре: найменша зміна.
- Погано: інтерфейс і далі отримує й відкидає тисячі записів інших проєктів.

### 3. Токен у кожному повідомленні

- Добре: видалений користувач відрізається одразу.
- Погано: запит у базу на кожну розсилку; сервер нічого не отримує від клієнта, щоб перевіряти.

### 4. Опитування API

- Добре: жодного окремого каналу.
- Погано: затримка й навантаження; ламає живі оновлення під час прогону.
