# ADR-0023: SDK під власною назвою Vision замість форку upstream VRT

| | |
|---|---|
| Статус | Proposed |
| Дата | 2026-11-01 |
| Хто вирішив | Дмитро Назаренко |

## Контекст

[ADR-0019](0019-sdk-upstream-plus-ui-tree-and-feature.md) тримав SDK як upstream VRT 4.3.1 плюс
два необов'язкові поля, щоб команди лише замінили jar. Тепер власник хоче відв'язати Vision від VRT:
у тестах видно `VisualRegressionTracker`, `VRT_*`, `vrt.json` і артефакт VRT. Специфікація —
[032](../specs/032-vision-sdk/spec.md).

## Чинники рішення

- Власні назви без VRT у пакеті, класах, конфігу й координатах.
- Перехід поступовий: тест, що ще не перейшов, працює на старому jar; еталони не скидаються.
- Мінімум змін за раз: спершу назви, нова поведінка — окремими кроками.
- Сервер не змінюється.

## Розглянуті варіанти

1. Перейменувати наявний SDK на місці, поведінку не чіпати
2. Новий SDK з нуля з новим API поруч із замороженим старим
3. Перейменувати плюс сумісні класи зі старими назвами

## Рішення

Обрано варіант 1. `sdk-java` стає Vision SDK: пакет `vision`, класи `Vision` і `VisionConfig`,
змінні `VISION_*`, файл `vision.json`, координати `vision:vision-sdk`, версія `1.0.0`. Методи,
параметри й запити до сервера ті самі. Старі назви не лишаються; тести, що не перейшли, лишаються на
jar `4.3.1-vision.2`, який більше не оновлюється. Нові методи й поведінка — наступні кроки зі своїми
специфікаціями, вже без обмеження «лише upstream».

## Наслідки

- Добре: власна назва в тестах і на CI; перехід — заміна залежності, імпортів, класу й змінних.
- Добре: пакети й артефакти різні, тож старий і новий jar живуть в одному проєкті.
- Добре: далі SDK розвивається без оглядки на upstream.
- Погано: `sdk-java` більше не оновлюється з upstream через subtree ([ADR-0001](0001-fork-as-subtree-monorepo.md)).
- Погано: правило 5 в [AGENTS.md](../../AGENTS.md) і [sdk-java/AGENTS.md](../../sdk-java/AGENTS.md)
  треба переписати разом з реалізацією.

## Як перевіряємо

Тести SDK перевіряють JSON, що йде на сервер, тими самими очікуваннями, що й для старого SDK
(REQ-032-07). Пошук «VisualRegressionTracker», «VRT_», «vrt.json» у `sdk-java/src` нічого не знаходить.

## Варіанти: за і проти

### 1. Перейменувати на місці

- Добре: малий і перевірюваний крок; одна кодова база.
- Погано: тести, що перейшли, змінюють імпорти й змінні CI.

### 2. Новий SDK з нуля

- Добре: чистий новий API одразу.
- Погано: великий крок; дві кодові бази; тести переписуються сильніше.

### 3. Перейменувати плюс сумісні класи

- Добре: старий код компілюється з новим jar.
- Погано: назви VRT лишаються в jar; власник обрав лише нові назви.
