# ADR-0023: Власний Vision SDK замість форку upstream VRT

| | |
|---|---|
| Статус | Proposed |
| Дата | 2026-11-01 |
| Хто вирішив | Дмитро Назаренко |

## Контекст

[ADR-0019](0019-sdk-upstream-plus-ui-tree-and-feature.md) тримав SDK як upstream VRT 4.3.1 плюс
два необов'язкові поля, щоб команди лише замінили jar. Тепер власник хоче відв'язати Vision від VRT:
у тестах видно `VisualRegressionTracker`, `VRT_*`, `vrt.json`, результат — це виняток із текстом,
а нові можливості сервера (формат дерева, щільність, Appium) у межах «upstream + поле» не додати.
Специфікація — [032](../specs/032-vision-sdk/spec.md).

## Чинники рішення

- Власний нейминг без VRT у пакеті, класах, конфігу й координатах.
- Наявні тести не ламаються й не втрачають еталонів: перехід поступовий.
- Простота: один короткий API, без шару сумісності.
- Сервер не змінюється для старого SDK.

## Розглянуті варіанти

1. Новий SDK з нуля поруч із замороженим старим
2. Перейменувати старий SDK на місці
3. Новий SDK плюс сумісний фасад зі старими класами

## Рішення

Обрано варіант 1. Новий модуль, пакет `vision`, координати `vision:vision-sdk` (і
`vision:vision-sdk-appium`), версія `1.0.0`, головний клас `Vision`. Конфіг лише `VISION_*` і
`vision.json`. Протокол сервера той самий. Старий `sdk-java` (`4.3.1-vision.N`) заморожений:
нових полів немає, лише критичні виправлення; ADR-0019 діє для нього, доки його не приберуть.

## Наслідки

- Добре: власний продукт у коді тестів; результат як значення; Appium одним рядком; нові поля
  сервера без оглядки на upstream.
- Добре: різні пакети, тож старий і новий jar живуть в одному проєкті, і команди переходять тест за
  тестом.
- Погано: дві кодові бази SDK на перехідний період; команди переписують виклики й змінні CI.
- Погано: правило 5 в [AGENTS.md](../../AGENTS.md) і [sdk-java/AGENTS.md](../../sdk-java/AGENTS.md)
  треба змінити, коли новий SDK реалізовано.

## Як перевіряємо

Тести нового SDK перевіряють JSON, що йде на сервер, і що назви полів збігаються з тими, що надсилає
старий SDK для тих самих значень (еталони не скидаються). `git diff` `sdk-java/` після цього ADR —
лише критичні виправлення.

## Варіанти: за і проти

### 1. Новий SDK з нуля поруч зі старим

- Добре: чистий API без спадку VRT; перехід поступовий; старі тести працюють.
- Погано: дві кодові бази, поки старий не приберуть.

### 2. Перейменувати на місці

- Добре: одна кодова база.
- Погано: усі тести ламаються одночасно, перехід «великим вибухом».

### 3. Новий SDK плюс фасад

- Добре: старий код компілюється з новим jar.
- Погано: фасад треба підтримувати; конфлікт класів, якщо старий jar теж у classpath; власник
  обрав «все нове».
