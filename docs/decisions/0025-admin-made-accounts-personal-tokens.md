# ADR-0025: Акаунти лише від адміністратора, токени Jira лише особисті

| | |
|---|---|
| Статус | Proposed |
| Дата | 2026-11-02 |
| Хто вирішив | Дмитро Назаренко |

## Контекст

Vision успадкував від upstream VRT відкриту реєстрацію: будь-хто, хто бачить адресу, сам
створює собі акаунт. Для внутрішнього інструмента команди це зайве: адміністратор дізнається
про людину вже після реєстрації й міняє їй роль.

[ADR-0010](0010-personal-jira-tokens.md) зробив токени Jira особистими, але лишив спільний токен
проєкту як запасний. З ним баг людини без власного токена заводиться від імені того, чий токен
у проєкті, з його правами, і в Jira не видно справжнього автора
([035](../specs/035-admin-accounts/spec.md)).

## Чинники рішення

- У Vision лише люди, яких завів адміністратор.
- У Jira — справжній автор і його права, без винятків.
- Upstream-код змінюємо мінімально ([ADR-0001](0001-fork-as-subtree-monorepo.md)); схему — лише
  додавальними змінами ([ADR-0003](0003-additive-schema-only.md)).

## Розглянуті варіанти

1. Лишити реєстрацію, але новим акаунтам давати роль без доступу до проєктів
2. Прибрати реєстрацію; акаунт створює адміністратор у Users; спільний токен Jira прибрати й
   стерти
3. Запрошення листом з посиланням на встановлення пароля

## Рішення

Друга опція. Маршрут реєстрації в API прибрано, натомість є створення акаунта, доступне лише
адміністратору; пароль задає він. Vision ходить у Jira лише з особистим токеном того, хто діє;
поля спільного токена й пошти з налаштувань проєкту прибрано, а збережені значення застосунок
стирає під час старту (ідемпотентно; колонки лишаються).

## Наслідки

- Добре: склад людей контролює адміністратор; у Jira завжди справжній автор.
- Добре: секрет проєкту, який бачили б у бекапах і налаштуваннях, зник.
- Погано: хто працював через спільний токен, має додати свій у профілі, інакше не заведе баг.
- Погано: пароль адміністратор передає людині сам, поза Vision.
- Погано: відкат Vision не поверне стерті спільні токени.

## Як перевіряємо

`backend/src/users/users.controller.spec.ts › has no route for signing oneself up`;
`backend/src/a11y/jira-access.spec.ts › never falls back to the project's shared token`;
`backend/src/projects/shared-jira-credentials.spec.ts › wipes stored shared Jira tokens and emails, and only them`.

## Варіанти: за і проти

### 1. Реєстрація з роллю без доступу

- Добре: нічого не прибирати з upstream.
- Погано: акаунти однаково з'являються без адміністратора; ролі без доступу у Vision немає.

### 2. Акаунти від адміністратора, лише особисті токени

- Добре: просто, без пошти й нових таблиць.
- Погано: пароль передають поза Vision.

### 3. Запрошення листом

- Добре: людина сама задає пароль.
- Погано: потрібен поштовий сервер і нова таблиця запрошень; власник не просив.
