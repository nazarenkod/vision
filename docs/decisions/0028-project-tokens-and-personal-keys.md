# ADR-0028: Два види ключів API: проєктний токен для SDK, персональний ключ — людина

| | |
|---|---|
| Статус | Proposed |
| Дата | 2026-11-05 |
| Хто вирішив | Дмитро Назаренко |

## Контекст

У Vision був один вид ключа: персональний API-ключ людини, успадкований від вихідного проєкту. З
ним працювали і CI (SDK), і CLI та MCP. CI тримався на ключі однієї людини й падав, щойно її
деактивували чи вона створювала новий ключ. Ключ, що витік із CI, відкривав усі проєкти людини.
При цьому ключ умів лише надсилати знімки й кілька читань: решта дій працювала тільки після входу
([046](../specs/046-project-tokens-and-personal-keys/spec.md)).

## Чинники рішення

- CI не залежить від конкретної людини, а витік з CI зачіпає один проєкт і лише прийом знімків.
- У журналах і Jira завжди справжній автор дії.
- SDK і його запити не змінюються ([ADR-0024](0024-own-vision-sdk.md), правило 5).
- Схема лише додавальна ([ADR-0003](0003-additive-schema-only.md)).
- Адміністрування й зміни облікового запису не можна виконати ключем, що витік.

## Розглянуті варіанти

1. Лишити один персональний ключ; для CI заводити технічних користувачів
2. Проєктний токен лише для SDK і персональний ключ, що діє як людина (крім адміністрування й
   облікового запису)
3. Токени з довільним набором прав (scopes) для будь-якого маршруту

## Рішення

Обрано варіант 2. Сервер розрізняє ключ за префіксом `vp_` у тому самому заголовку `apiKey`. З
проєктним токеном допускаються лише маршрути SDK у його проєкті; персональний ключ проходить ті
самі перевірки ролі й доступу, що й вхід, але маршрути адміністрування й облікового запису його
не приймають.

## Наслідки

- Добре: CI переживає зміни в команді; витік токена з CI зачіпає один проєкт і лише прийом знімків.
- Добре: CLI, MCP і скрипти можуть те саме, що людина в інтерфейсі; автором дій записується людина.
- Погано: витік персонального ключа тепер дає більше, ніж раніше: усі дії людини в її проєктах.
  Пом'якшення: ключ деактивованої людини не діє, а новий ключ створюється лише після входу.
- Погано: кожен новий маршрут має свідомо обрати, чи приймає він ключ; це перевіряє тест маршрутів.

## Як перевіряємо

Тест маршрутів API (`backend/src/projects/project-access.routes.spec.ts` разом із новими
перевірками 046): проєктний токен отримує відмову на кожному маршруті, крім маршрутів SDK, а
маршрути адміністрування й облікового запису відмовляють персональному ключу. Повний перелік
тестів — у [дизайні 046](../specs/046-project-tokens-and-personal-keys/design.md).

## Варіанти: за і проти

### 1. Технічні користувачі для CI

- Добре: нічого нового в моделі даних.
- Погано: технічний користувач має роль і доступ людини, тож його ключ відкриває все, що відкриває
  роль editor; ним можна увійти чи погодити зміни.

### 3. Довільні права для токенів

- Добре: гнучко.
- Погано: інтерфейс і перевірки набагато складніші, а потреби, крім SDK, немає.
