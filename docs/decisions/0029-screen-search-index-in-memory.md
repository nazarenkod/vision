# ADR-0029: Пошук екранів — індекс у пам'яті API, а не таблиця елементів у базі

| | |
|---|---|
| Статус | Proposed |
| Дата | 2026-11-15 |
| Хто вирішив | Дмитро Назаренко (пропозиція до затвердження) |

## Контекст

[053](../specs/053-screen-search/spec.md) шукає текст, підпис і селектор у UI-деревах останніх
еталонів проєкту. Дерева лежать у файлах (gzip JSON), а не в базі («звіти й дерева — у файлах,
у базі — лічильники», backend/AGENTS.md). Проєкт Android — до 2000 перевірок × 3 пристрої,
тобто ~6000 дерев по ~200 видимих вузлів. Відкрити й розпакувати 6000 файлів на кожен запит —
десятки секунд, а SC-053-01 вимагає 2 s.

## Чинники рішення

- Час відповіді 2 s на 95 % запитів (SC-053-01).
- Лише додавальні міграції ([ADR-0003](0003-additive-schema-only.md)), бекапи без зайвого
  ([ADR-0012](0012-backups-without-secrets.md)): що більше в базі, то довший бекап.
- Селектор `xpath:` потребує цілого дерева з батьками, а не плаского переліку вузлів.
- Один процес API на машині (Vision стоїть поруч із VRT, без кластера).

## Розглянуті варіанти

1. Таблиця елементів еталонів у Postgres з триграмним індексом.
2. Індекс у пам'яті API: видимі вузли останніх еталонів кожного проєкту, зібрані з файлів при
   першому пошуку й оновлювані за назвою файла дерева.
3. Без індексу: розбирати файли на кожен запит.

## Рішення

Обрано варіант 2, бо він дає потрібний час без нової таблиці на мільйон рядків і розширення
Postgres, а дерево для `xpath:` уже є в пам'яті поруч.

## Наслідки

- Добре: жодної міграції; бекап не росте; індекс завжди з тих самих файлів, що й порівняння.
- Добре: селектори працюють тим самим кодом, що й правила (SC-053-03).
- Погано: перший пошук у проєкті після старту API повільніший (збирання індексу); тому API
  збирає індекси у фоні після старту.
- Погано: пам'ять — оцінка ~60–100 МБ на великий проєкт; межа на кількість проєктів в індексі
  (найдавніше використаний викидається).
- Погано: два процеси API бачили б різні індекси — прийнятно, поки API один.

## Як перевіряємо

Тест сервісу пошуку: після зміни еталона наступний пошук бачить нове дерево; навантажувальна
перевірка `manual:` на копії проду з 6000 деревами — час першого й повторного пошуку.

## Варіанти: за і проти

### 1. Таблиця в Postgres

- Добре: індекс переживає перезапуск; масштабується на кілька процесів.
- Погано: ~1,2 млн рядків, `pg_trgm`, заповнення й чистка при кожному approve; бекап росте;
  `xpath:` однаково потребує файла дерева.

### 3. Без індексу

- Добре: нічого нового.
- Погано: десятки секунд на запит, не проходить SC-053-01.
