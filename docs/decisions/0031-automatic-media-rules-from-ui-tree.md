# ADR-0031: Правила, яких ніхто не створював: медіа-елементи за типом з UI-дерева

| | |
|---|---|
| Статус | Proposed |
| Дата | 2026-11-16 |
| Хто вирішив | Дмитро Назаренко |

## Контекст

Досі все, що змінює порівняння, робила людина: правило елемента, область, «порівнювати лише»,
нестабільний текст. Єдиний виняток — системні панелі, і їх можна вимкнути одним прапорцем.
Специфікація [060](../specs/060-media-frame-only/spec.md) вимагає, щоб Vision сам перестав
порівнювати кадр відео, анімацій і `canvas` у кожній перевірці кожного проєкту, і щоб це було
типово ввімкнено. Це перше правило, яке діє без жодної дії людини на конкретних елементах, тож
треба домовитись, як такі правила влаштовані.

## Чинники рішення

- Порівняння має лишатися детермінованим і поясненим (ADR-0007): видно, що не порівнювалось і
  чому.
- Автоматичне правило не повинно мовчки вимкнути порівняння цілої перевірки.
- Людина мусить мати змогу скасувати автоматику для одного елемента, перевірки й проєкту.
- Без міграцій (ADR-0003) і без змін SDK (правило 5).

## Розглянуті варіанти

1. Автоматичні правила обчислюються з типу елемента при кожному порівнянні, мають джерело «авто»
   і поступаються будь-якому правилу людини.
2. Автоматика при першій зустрічі створює звичайні правила в налаштуваннях проєкту.
3. Лише пропозиції в рев'ю, як підказки щодо шуму ([054](../specs/054-rules-from-noise-history/spec.md)).

## Рішення

Обрано варіант 1:

- Автоматичне правило ніде не зберігається. Його щоразу обчислює чиста функція з дерева й
  налаштувань проєкту.
- В інтерфейсі воно позначене джерелом «авто».
- Воно ніколи не перекриває правило людини.
- Воно не бере елемент площею понад половину знімка.
- Його вимикає один вимикач проєкту, а для одного елемента — правило «Увесь вміст».

## Наслідки

- Добре: перевірки з відео перестають шуміти одразу, без налаштувань.
- Добре: покращений перелік типів діє на старі перевірки без перенесення даних.
- Погано: результат залежить від версії Vision. Ширший перелік у новій версії може змінити, що
  порівнюється, без дії людини. Тому кожна зміна переліку — через специфікацію.
- Погано: справжня зміна вмісту медіа (чорний кадр) не ловиться, доки немає перевірки руху.
- Наступні автоматичні правила (наприклад, шимери чи каруселі) роблять так само: джерело «авто»,
  поступаються людині, мають ліміт площі й вимикач.

## Як перевіряємо

Тести backend/src/ui-tree/media-elements.spec.ts (з'являться з реалізацією 060): правило людини
й ігнорований предок перемагають, елемент понад 50 % знімка не береться, вимкнений проєкт
вимикає перелік. Знімок поведінки `structure.characterization` фіксує, що автоматика додає.

## Варіанти: за і проти

### 1. Обчислювати при кожному порівнянні

- Добре: немає збережених даних, які старіють; поступається людині за побудовою.
- Погано: результат залежить від версії переліку.

### 2. Створювати звичайні правила

- Добре: усе, що діє, видно в налаштуваннях як правила.
- Погано: сотні правил на кожен проєкт; запис у налаштування під час порівняння; незрозуміло,
  хто їх автор і коли прибирати.

### 3. Лише пропозиції

- Добре: нічого не змінюється без людини.
- Погано: шум лишається в кожній новій перевірці, поки хтось не натисне; саме цю проблему
  специфікація й вирішує.
