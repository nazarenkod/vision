банку, як розгорнути й прийняти, що лишається відкритим. Почніть звідси; кожен документ нижче
стоїть окремо.

## Перенесення коду в git банку

Код передається без історії комітів: один коміт з поточним станом.

1. На машині з цим репозиторієм, на перевіреному коміті:

   ```bash
   ./scripts/export-without-history.sh ../vision-bank
   ```

   Скрипт бере лише відстежувані git файли (`git archive`), створює новий репозиторій з одним
   комітом і нікуди не пушить.

2. Підключити git банку й запушити:

   ```bash
   cd ../vision-bank
   git remote add vision https://git.bank.example/qa/vision.git
   git push -u vision main
   ```

3. Змінити в новому репозиторії адресу, яку знають агенти й документація:
   - `.claude/repository.json` — `pushRemote` (назва remote, тут `vision`) і `repository`
     (адреса без схеми);
   - `DEPLOY.md` §2 — адреса для `git clone`;
   - `NOTICE` — за потреби додати рядок про банк як нового правовласника змін; рядки про
     Visual Regression Tracker лишити.

4. CI: `.github/workflows/docs.yml` — для GitHub. У GitLab чи Jenkins банку — той самий крок
   `python3 -I scripts/check-docs.py` і тести скриптів; повна перевірка — `python3 -I scripts/verify.py`.

5. AI-агенти: якщо в банку їх не використовують, `AGENTS.md`, `CLAUDE.md` і `.claude/` можна
   лишити як документацію правил або видалити. Правила з `AGENTS.md` (лише додавальні міграції,
   робочий VRT лише читається, секрети не виходять із сервера) діють і для людей.

## Розгортання

1. Підготувати сервер і доступи за [вимогами](requirements.md), погодити з ІБ [безпеку](security.md).
2. Розгорнути за [DEPLOY.md](../../DEPLOY.md): `.env.demo` з [налаштувань](configuration.md),
   збирання з дзеркал банку (`VISION_NPM_REGISTRY`, `VISION_PRISMA_ENGINES_MIRROR`, `VISION_EXTRA_CA_FILE`).
3. Якщо Vision переходить з робочого VRT або зі старішого Vision — [інструкція переходу](../guides/bank-cutover.md).
   Інакше Vision стартує з порожньою базою і першим адміністратором (`DEFAULT_USER_*`).
4. TLS на зворотному проксі, LDAP або SSO, `VISION_JIRA_HOSTS`, бекапи у внутрішнє сховище —
   [експлуатація](operations.md).

## Чек-лист приймання

Технічне:

- [ ] `./scripts/vision.sh ps -a`: `api`, `ui`, `postgres` — `Up`, `migration` — `Exited (0)`.
- [ ] `GET <DEMO_API_URL>/health` → `{"status":"ok"}` через проксі банку по HTTPS.
- [ ] Вхід: локальний адміністратор і людина з LDAP/SSO; пароль першого адміністратора змінено.
- [ ] Новий користувач не бачить проєктів, доки не дали доступ; після доступу — бачить.
- [ ] Автотест із Java SDK 1.0.0 надсилає знімок з UI-деревом; збірка з'являється, порівняння й
      зміни видно; approve, reject і Undo працюють.
- [ ] Баг доступності заводиться в Jira банку (тестовий проєкт Jira).
- [ ] Ручна перевірка з `vision.py` (CLI) доходить до Vision.
- [ ] Бекап у внутрішнє сховище пройшов; відновлення на тестовій машині — за [backup-trial](../guides/backup-trial.md).
- [ ] Якщо був перехід з VRT: `./scripts/vision-check-cutover.sh` без помилок.
- [ ] Логи API йдуть у систему збору логів банку; моніторинг `/health` налаштовано.

Безпека й відповідність:

- [ ] ІБ погодила [залишкові ризики](security.md#залишкові-ризики).
- [ ] Образи `vision-api`, `vision-ui`, `vision-migration` проскановано сканером банку.
- [ ] `AI_PROVIDER` — `none` або `ollama` (або Gemini з погодженням ІБ).
- [ ] Юристи погодили [ліцензії](third-party-licenses.md).
- [ ] `VISION_SECRET_KEY`, `JWT_SECRET`, `VISION_MASTER_*` — у сховищі секретів банку.

Розробка (для команди, що супроводжує код):

- [ ] `python3 -I scripts/verify.py` зелений на машині розробника банку
      ([development](../guides/development.md), [testing](../guides/testing.md)).
- [ ] Контрольний сценарій `./scripts/control-scenario.sh` зелений.
