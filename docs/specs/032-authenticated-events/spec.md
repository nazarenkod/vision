## Контекст і проблема

Інтерфейс оновлює збірки й знімки без перезавантаження сторінки: сервер надсилає по постійному
з'єднанню подій кожну нову чи змінену збірку і кожен створений, змінений чи видалений знімок —
цілим записом, з назвами перевірок, гілками, пристроями, статусами й шляхами до зображень.

Це з'єднання успадковано з upstream VRT, і воно нічого не перевіряє:

- відкрити його може будь-хто, хто дістається до адреси Vision, без входу й без ключа;
- кожне з'єднання отримує події всіх проєктів, а не того, що відкритий у інтерфейсі;
- REST API тим часом вимагає токен входу або ключ API на кожен запит.

Тобто дані, які API віддає лише користувачам, будь-хто може слухати наживо. Під час роботи над
специфікацією 031 публічна сторінка звіту через це свідомо не використовує
події. Крім того, інтерфейс зараз отримує й відкидає в себе події всіх проєктів: під час великого
прогону в іншому проєкті це тисячі зайвих записів на кожного відкритого користувача.

## Користувацькі історії

### US-1 (P1): Слухати події може лише той, хто увійшов

Як власник Vision, я хочу, щоб з'єднання подій вимагало того самого входу, що й API, щоб дані
збірок не бачив ніхто без облікового запису.

- **Чому P1:** це закриває витік; без цього решта не має сенсу.
- **Незалежна перевірка:** відкрити з'єднання подій без токена, з чужим чи простроченим токеном —
  сервер відхиляє; з токеном, який видав вхід у Vision, — приймає.
- **Сценарії приймання:**
  1. **Дано** Vision працює, **коли** клієнт відкриває з'єднання подій без токена, **тоді** сервер
     відхиляє з'єднання і клієнт не отримує жодної події.
  2. **Дано** токен, підписаний не ключем Vision або з терміном дії, що сплив, **коли** клієнт
     відкриває з ним з'єднання, **тоді** сервер відхиляє з'єднання.
  3. **Дано** користувач увійшов (будь-яка роль: адміністратор, редактор, гість), **коли** його
     інтерфейс відкриває з'єднання з його токеном, **тоді** сервер приймає з'єднання.
  4. **Дано** відкрите з'єднання, **коли** спливає термін дії його токена, **тоді** сервер
     розриває з'єднання.

### US-2 (P1): Інтерфейс далі оновлюється наживо

Як QA, я хочу, щоб збірки й знімки, як і раніше, з'являлися й змінювались без перезавантаження,
щоб захист не зламав щоденну роботу.

- **Чому P1:** без живих оновлень інтерфейс неможливо використовувати під час прогону.
- **Незалежна перевірка:** увійти, відкрити проєкт, запустити прогін — нові знімки з'являються,
  рішення по знімку змінює його статус на екрані без перезавантаження.
- **Сценарії приймання:**
  1. **Дано** користувач увійшов і відкрив проєкт, **коли** SDK надсилає знімки в нову збірку,
     **тоді** збірка й знімки з'являються в інтерфейсі без перезавантаження сторінки.
  2. **Дано** користувач не входив, **коли** він відкриває сторінку входу, **тоді** інтерфейс не
     відкриває з'єднання подій.
  3. **Дано** користувач вийшов і увійшов іншим обліковим записом без перезавантаження, **коли**
     приходять події, **тоді** з'єднання відкрите з токеном нового входу.
  4. **Дано** сервер відхилив з'єднання через недійсний токен, **коли** це стається, **тоді**
     інтерфейс поводиться так само, як на відмову API: виходить і показує сторінку входу.

### US-3 (P2): Події лише проєкту, який відкритий

Як QA, я хочу отримувати події лише того проєкту, з яким працюю, щоб великий прогін в іншому
проєкті не навантажував мій інтерфейс і щоб з'єднання не несло зайвих даних.

- **Чому P2:** закриває надлишкову розсилку; захист від стороннього слухача дає вже US-1.
- **Незалежна перевірка:** відкрити два інтерфейси на різних проєктах, надіслати знімок у перший —
  подію отримує лише інтерфейс першого проєкту.
- **Сценарії приймання:**
  1. **Дано** інтерфейс відкрито на проєкті A, **коли** змінюється знімок у проєкті B, **тоді**
     інтерфейс не отримує цієї події.
  2. **Дано** інтерфейс відкрито на проєкті A, **коли** користувач перемикається на проєкт B,
     **тоді** він отримує події B і більше не отримує подій A.
  3. **Дано** з'єднання обірвалось і відновилось, **коли** знімок змінюється в обраному проєкті,
     **тоді** інтерфейс отримує подію без перезавантаження сторінки.

## Граничні випадки

- Користувача видалили, поки його з'єднання відкрите? → нові з'єднання й нові підписки
  відхиляються (REQ-032-01, REQ-032-11 перевіряє користувача теж); уже відкрите з'єднання живе
  не довше за термін дії токена (REQ-032-04). Так само зараз поводиться й API для вже виданого
  токена до наступного запиту.
- Токен сплив, поки вкладка відкрита? → сервер розриває з'єднання (REQ-032-04), інтерфейс пробує
  відновити його з тим самим токеном, отримує відмову й виходить (REQ-032-08) — як і на першому
  ж запиті до API.
- Знімок у старих записах без власного посилання на проєкт? → подія йде підписаним на проєкт його
  збірки (REQ-032-09).
- Видалення збірки? → подію отримують лише підписані на її проєкт (REQ-032-09).
- Дві вкладки одного користувача на різних проєктах? → кожна отримує події лише свого проєкту
  (REQ-032-09, REQ-032-10).
- Кілька екземплярів сервера за спільним каналом? → підписка працює так само, бо подія
  розсилається в межах проєкту на всіх екземплярах (REQ-032-09).
- Сторінка списку проєктів, де жоден проєкт не обраний? → з'єднання відкрите, але подій про
  збірки й знімки не отримує (REQ-032-09); на цій сторінці вони й не показуються.
- Публічна сторінка звіту з 031? → далі не відкриває з'єднання
  подій (REQ-032-06 для неї теж: на ній немає входу).

## Ключові сутності

- **З'єднання подій** — постійне з'єднання інтерфейсу з сервером, по якому приходять події
  `build_created`, `build_updated`, `build_deleted`, `testRun_created`, `testRun_updated`,
  `testRun_deleted`. Належить одному входу користувача; живе не довше за термін дії його токена.
- **Підписка на проєкт** — до якого проєкту з'єднання хоче отримувати події; одна на з'єднання,
  змінюється разом з обраним проєктом.
- **Токен входу** — той самий, що видає вхід у Vision і що API приймає в заголовку авторизації;
  має термін дії.

## Критерії успіху

| ID | Критерій |
|---|---|
| SC-032-01 | Клієнт без дійсного токена входу отримує 0 подій: з'єднання відхилене до першої події. |
| SC-032-02 | Новий знімок і рішення по знімку з'являються в інтерфейсі, що увійшов, не пізніше ніж за 5 с, як і до зміни. |
| SC-032-03 | Інтерфейс, відкритий на одному проєкті, отримує 0 подій про збірки й знімки інших проєктів. |

## Припущення

- Події наживо потрібні лише вебінтерфейсу Vision. SDK, CLI і MCP їх не слухають, тому ключ API
  для з'єднання подій не потрібен (REQ-032-03).
- Інтерфейс upstream VRT із сервером Vision не використовується: Vision постачає власний
  інтерфейс. Тому клієнт upstream без токена, якого сервер тепер відхилить, — не регресія.
- Будь-який користувач, що увійшов, і зараз читає через API всі проєкти; підписка на проєкт
  обмежує обсяг розсилки, а не права доступу. Права на окремі проєкти Vision не має.

## Поза межами

- Права доступу до окремих проєктів (хто який проєкт бачить) — їх немає і в API; окрема фіча.
- Події наживо для публічного звіту 031 — звіт оновлюється
  запитом, а не з'єднанням подій.
- Перевірка, що користувач досі існує, на кожну подію: обмежуємося моментом з'єднання й підписки
  та терміном дії токена, щоб не ходити в базу на кожну розсилку.
- Зміна складу полів у подіях — вони й далі цілі записи, як віддає API.
