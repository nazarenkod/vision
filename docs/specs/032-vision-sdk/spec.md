## Контекст і проблема

Автотести надсилають знімки через форк upstream Java SDK VRT 4.3.1 з двома доданими полями
([012](../012-java-sdk/spec.md), [ADR-0019](../../decisions/0019-sdk-upstream-plus-ui-tree-and-feature.md)).
Усе інше — нейминг і поведінка VRT:

- класи `VisualRegressionTracker`, `TestRunOptions`, пакет `io.visual_regression_tracker`,
  змінні `VRT_*` і файл `vrt.json`: команди бачать чужий продукт, хоча працюють з Vision;
- знімок приймається лише як base64-рядок, тож кожен тест сам кодує скріншот;
- результат перевірки — виняток із посиланням у тексті: щоб дізнатися статус, тест розбирає рядок;
- поле з друкарською помилкою `diffTollerancePercent`;
- сервер Vision уже приймає формат UI-дерева й щільність екрана, але SDK їх не надсилає;
- для Appium тест щоразу вручну збирає скріншот, page source, пристрій і OS.

Власник вирішив відв'язатися від VRT: новий SDK з власним неймингом, написаний з нуля. Старий
jar лишається для тестів, які ще не перейшли.

## Як це виглядає в тесті

Публічні назви — частина контракту з командами, тому вони тут, а не в дизайні.

```java
try (Vision vision = Vision.start()) {                    // збірка; налаштування — з VISION_* або vision.json
    vision.check("Checkout.Payment", Snapshot.builder()
            .image(screenshotPng)                         // байти PNG або файл
            .uiTree(driver.getPageSource())
            .device("Pixel 7").os("Android 15")
            .feature("Checkout")
            .build());                                    // нова або змінена перевірка — тест падає
}                                                         // кінець блоку завершує збірку

// з модулем для Appium — одним рядком:
vision.check("Checkout.Payment", AppiumSnapshot.of(driver).feature("Checkout").build());
```

| Що | Назва |
|---|---|
| Головний об'єкт — запущена збірка | `Vision`: `start()`, `start(VisionConfig)`, `check(name, snapshot)`, `finish()`, `close()` |
| Налаштування | `VisionConfig`: `url`, `apiKey`, `project`, `branch`, `ciBuildId`, `soft`, `timeoutSeconds` |
| Змінні оточення | `VISION_URL`, `VISION_API_KEY`, `VISION_PROJECT`, `VISION_BRANCH`, `VISION_CI_BUILD_ID`, `VISION_SOFT`, `VISION_TIMEOUT_SECONDS` |
| Файл налаштувань | `vision.json` у робочій теці |
| Знімок | `Snapshot`: `image`, `uiTree`, `platform`, `device`, `os`, `density`, `feature`, `tags`, `tolerancePercent`, `ignore` |
| Результат | `CheckResult`: `status()`, `url()`, `imageUrl()`, `baselineUrl()`, `diffUrl()`, `diffPercent()` |
| Статуси | `PASSED`, `NEW`, `CHANGED`, `REJECTED` |
| Помилка | `VisionException` (має `result()`, коли сервер відповів результатом перевірки) |
| Appium | `AppiumSnapshot.of(driver)` — заповнений `Snapshot` з драйвера |
| Пакет і координати | пакет `vision`, Maven `vision:vision-sdk:1.0.0`, модуль Appium — `vision:vision-sdk-appium:1.0.0` |

## Користувацькі історії

### US-1 (P1): Надіслати знімок через Vision SDK

Як автоматизатор, я хочу підключити Vision SDK і надсилати знімки через `Vision`, щоб працювати з
інструментом під його власною назвою, без класів і змінних VRT.

- **Чому P1:** без цього нового SDK немає.
- **Незалежна перевірка:** у порожньому Maven-проєкті на JDK 11 підключити `vision-sdk`, задати
  `VISION_URL`, `VISION_API_KEY`, `VISION_PROJECT`, надіслати один знімок → у Vision з'являється
  збірка з перевіркою; після кінця блоку збірка завершена.
- **Сценарії приймання:**
  1. **Дано** змінні `VISION_*`, **коли** тест викликає `Vision.start()`, **тоді** у проєкті
     з'являється запущена збірка на гілці з `VISION_BRANCH`.
  2. **Дано** запущену збірку, **коли** тест викликає `check` з PNG і UI-деревом, **тоді** знімок і
     дерево з'являються в цій збірці.
  3. **Дано** запущену збірку, **коли** блок `try` закінчився (і нормально, і з винятком), **тоді**
     збірка завершена.
  4. **Дано** лише `VRT_APIURL`, `VRT_APIKEY` і `vrt.json`, **коли** тест викликає `Vision.start()`,
     **тоді** виняток називає відсутню `VISION_URL`; старі назви не читаються.

### US-2 (P1): Перейти зі старого SDK без нових еталонів

Як лід QA, я хочу переводити тести на Vision SDK поступово, щоб наявні еталони лишились і жоден
тест не зламався через перехід.

- **Чому P1:** якщо перехід скидає еталони чи ламає тести, команди не перейдуть.
- **Незалежна перевірка:** перевірка з еталоном зі старого SDK → той самий тест через Vision SDK з
  тими самими назвою, пристроєм, OS і тегами → статус `PASSED` проти того самого еталона.
- **Сценарії приймання:**
  1. **Дано** еталон, створений старим SDK, **коли** Vision SDK надсилає знімок з тими самими
     назвою, тегами, пристроєм і OS, **тоді** знімок порівнюється з цим еталоном.
  2. **Дано** проєкт, де одні тести на старому SDK, а інші на новому, **коли** обидва jar стоять у
     одному проєкті тестів, **тоді** обидва працюють і не конфліктують.

### US-3 (P1): Результат перевірки як значення

Як автоматизатор, я хочу отримувати статус і посилання перевірки з об'єкта результату, щоб не
розбирати текст винятку.

- **Чому P1:** це головна зміна поведінки, з якою тести пишуться інакше.
- **Незалежна перевірка:** у режимі `soft` надіслати новий знімок → `check` повертає `NEW` і
  посилання на рев'ю, тест не падає; без `soft` → `VisionException`, з якої видно той самий результат.
- **Сценарії приймання:**
  1. **Дано** знімок, що збігся з еталоном, **коли** `check` завершився, **тоді** повертається
     `PASSED` і посилання на знімок.
  2. **Дано** нову перевірку без еталона, **коли** `check` без `soft`, **тоді** кидається
     `VisionException` з `NEW` і посиланням на рев'ю.
  3. **Дано** відмінність від еталона в режимі `soft`, **коли** `check` завершився, **тоді**
     повертається `CHANGED` з відсотком різниці й посиланнями, у лог іде попередження з посиланням.
  4. **Дано** недозволений пристрій ([029](../029-allowed-devices/spec.md)), **коли** `check` у будь-якому
     режимі, **тоді** кидається `VisionException` з текстом сервера.

### US-4 (P2): Знімок з Appium одним рядком

Як автоматизатор мобільних тестів, я хочу будувати знімок з драйвера Appium одним викликом, щоб не
збирати скріншот, дерево, платформу, пристрій і OS вручну в кожному тесті.

- **Чому P2:** без цього SDK працює, але тести довші й легше забути дерево чи OS.
- **Незалежна перевірка:** на емуляторі Android і симуляторі iOS викликати
  `AppiumSnapshot.of(driver)` → у Vision знімок має дерево, правильну платформу, пристрій, OS, а для
  Android — щільність.
- **Сценарії приймання:**
  1. **Дано** сесію Appium на Android, **коли** тест надсилає `AppiumSnapshot.of(driver)`, **тоді**
     знімок має скріншот, дерево, платформу Android, пристрій, OS і щільність екрана.
  2. **Дано** сесію на iOS, **коли** так само, **тоді** знімок має платформу iOS, пристрій і OS.
  3. **Дано** тест, якому потрібна інша назва пристрою, **коли** він задає `device(...)` після
     `AppiumSnapshot.of(driver)`, **тоді** надсилається його значення.
  4. **Дано** проєкт тестів без Appium, **коли** він підключає лише `vision-sdk`, **тоді** Appium
     йому не потрібен.

## Граничні випадки

- Тест забув `finish` і не використав try-with-resources → збірка лишається запущеною, як у
  старому SDK; SDK не завершує її сам. [ПОТРЕБУЄ УТОЧНЕННЯ: завершувати збірку при зупинці JVM,
  якщо тест цього не зробив?]
- `finish` викликано двічі, або `close` після `finish` → нічого не відбувається (REQ-032-07).
- Помилка мережі при завершенні збірки в `close`, коли тест уже падає з іншою причиною → початкова
  причина лишається головною, помилку завершення видно як пригнічену (REQ-032-07).
- Знімок 5 МБ PNG з деревом 2 МБ → дерево стиснуте, запит не перевищує ліміту сервера (REQ-032-11).
- Сесія Appium без щільності екрана або з порожнім page source → знімок надсилається без цих полів
  (REQ-032-26, REQ-032-11).
- Сервер повернув статус, якого SDK не знає (новий у майбутньому) → [ПОТРЕБУЄ УТОЧНЕННЯ: вважати
  `CHANGED` чи кидати виняток?]
- Тест на старому й новому SDK в одній збірці CI з тим самим `ciBuildId` → обидва пишуть в одну
  збірку (REQ-032-16, REQ-032-20).
- `VISION_SOFT=yes` чи інше нерозпізнане значення → виняток з назвою змінної, а не тиха `false`
  (REQ-032-03).

## Ключові сутності

- **Збірка** — один прогін тестів; `Vision` існує лише для запущеної збірки, тож перевірки без
  старту неможливі за побудовою.
- **Знімок** — зображення плюс необов'язкові дерево, платформа, пристрій, OS, щільність, фіча, теги,
  допуск і області без порівняння.
- **Результат перевірки** — статус, посилання, відсоток різниці.
- **Перевірка** — назва + теги + пристрій ([001](../001-check-identity/spec.md)); не змінюється.

## Припущення

- Протокол сервера (адреси запитів, заголовки авторизації, поля JSON) не змінюється; його
  перейменування — окреме рішення.
- Нові тести пишуть лише для мобільних застосунків, тож браузер і viewport у знімку не потрібні.
  [ПОТРЕБУЄ УТОЧНЕННЯ: чи передає хтось зараз `browser` або `viewport`? Якщо так, без них еталони
  цих перевірок не знайдуться (REQ-032-18), і поля треба додати.]
- Старий SDK (`4.3.1-vision.2`) заморожений: лише виправлення критичних помилок, нових полів немає.
- Kotlin-тести користуються тим самим Java API.

## Поза межами

- Перейменування REST API і заголовків сервера — окреме рішення, щоб не ламати старий SDK.
- Сумісний фасад зі старими класами `VisualRegressionTracker` у новому jar — власник обрав
  «все нове».
- Читання `VRT_*` і `vrt.json` — свідомо ні, рішення власника.
