## Контекст і проблема

Автотести надсилають знімки через форк вихідного Java SDK 4.3.1 з двома доданими полями
([012](../012-java-sdk/spec.md)). Головний об'єкт у кожному тесті — `VisualRegressionTracker`, а
його налаштування — `VisualRegressionTrackerConfig`: у коді видно назву чужого продукту. Власник
вирішив відв'язуватися від VRT поступово, і перший крок — лише ці два класи.

## Що змінюється

| Було | Стало |
|---|---|
| `VisualRegressionTracker` | `Vision` |
| `VisualRegressionTrackerConfig` | `VisionConfig` |
| `VisualRegressionTrackerConfig.builder()` | `VisionConfig.builder()` |

Усе інше без змін: пакет, методи (`start`, `track`, `stop`), `TestRunOptions`, `TestRunResult`,
`TestRunStatus`, `TestRunException`, `IgnoreAreas`, поля налаштувань, змінні `VRT_*`, файл
`vrt.json`, Maven-координати. Нова версія jar — `4.3.1-vision.3`.

```java
import io.visual_regression_tracker.sdk_java.Vision;
import io.visual_regression_tracker.sdk_java.VisionConfig;

Vision vision = new Vision(VisionConfig.builder().apiUrl(url).apiKey(key).project("Mobile").build());
vision.start();
vision.track("Checkout.Payment", screenshotBase64, TestRunOptions.builder().uiTree(xml).build());
vision.stop();
```

## Користувацькі історії

### US-1 (P1): Головні класи під назвою Vision

Як автоматизатор, я хочу створювати в тестах `Vision` і `VisionConfig`, щоб головний об'єкт
називався як наш інструмент.

- **Чому P1:** це і є зміна.
- **Незалежна перевірка:** у тесті замінити `VisualRegressionTracker` на `Vision` і
  `VisualRegressionTrackerConfig` на `VisionConfig`, підключити jar `4.3.1-vision.3` → тест
  компілюється й надсилає знімки, як раніше.
- **Сценарії приймання:**
  1. **Дано** тест на `4.3.1-vision.2`, **коли** jar замінено на `4.3.1-vision.3`, а дві назви
     класів — на нові, **тоді** тест працює як раніше, з тими самими змінними `VRT_*` і `vrt.json`.
  2. **Дано** еталон, створений попереднім jar, **коли** тест на новому jar надсилає знімок з тими
     самими значеннями, **тоді** знімок порівнюється з тим самим еталоном.

## Вимоги

| ID | Історія | Вимога |
|---|---|---|
| REQ-033-01 | US-1 | SDK ПОВИНЕН мати головний клас `Vision` і клас налаштувань `VisionConfig` замість `VisualRegressionTracker` і `VisualRegressionTrackerConfig`, без класів зі старими назвами. |
| REQ-033-02 | US-1 | `Vision` і `VisionConfig` ПОВИННІ мати ті самі конструктори, методи, поля й поведінку, що й класи, які вони замінюють, зокрема ті самі запити до сервера. |
| REQ-033-03 | US-1 | SDK ПОВИНЕН брати налаштування з тих самих джерел, що й раніше: код, змінні `VRT_*`, `vrt.json`. Замінено 2026-11-05 [040](../040-uitree-limits-and-sdk-names/spec.md) REQ-040-11: змінні `VISION_*` і `vision.json`, старих SDK не читає. |

## Граничні випадки

- Тест лишив стару назву класу → не компілюється з новим jar; лишається на `4.3.1-vision.2`, доки
  не перейде (REQ-033-01).
- Тест наслідує `VisualRegressionTracker` (захищені поля, `getRequest`, `handleResponse`) → після
  заміни назви на `Vision` наслідування працює так само (REQ-033-02).

| ID | Критерій |

| SC-033-01 | Перехід тесту — заміна двох назв класів і їхніх імпортів, нічого більше. |
| SC-033-02 | Перехід не створює нових еталонів: 0 знімків зі статусом `new` для перевірок, що мали еталон. |

## Припущення

- Старий jar `4.3.1-vision.2` лишається доступним для тестів, які ще не перейшли.

## Поза межами

- Пакет, методи, `TestRun*`, змінні `VISION_*`, `vision.json`, нові Maven-координати, нові
  параметри й можливості — наступні кроки, кожен окремо, за рішенням власника.
- Класи зі старими назвами поруч із новими — власник обрав лише нові назви.
