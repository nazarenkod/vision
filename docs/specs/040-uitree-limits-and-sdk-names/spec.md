## Контекст і проблема

Разом зі знімком автотест надсилає UI-дерево екрана (Appium page source), стиснуте або ні.
Сервер його розпаковує й розбирає. Аудит знайшов, що це найслабше місце перед заведенням у
банківський контур:

- **Дерево-бомба.** Кілька кілобайтів стиснутого запиту розгортаються в гігабайти. Сервер
  розпаковує їх повністю й на цей час перестає відповідати всім. Достатньо одного запиту з
  будь-яким API-ключем, тобто з будь-якого CI.
- **XML-сутності.** Дерево може оголосити сутності, що розгортаються одна в одну («billion
  laughs»). Бібліотека розбору має відомі критичні вразливості саме тут, і сканер банку покаже
  їх як critical.
- **Чужа назва в SDK.** Тестові проєкти імпортують пакет `io.visual_regression_tracker…`, беруть
  налаштування зі змінних `VRT_*` і файла `vrt.json`, а лог пише «Visual Regression Tracker».
  Власник хоче, щоб від VRT нічого не лишилось, крім `LICENSE` і `NOTICE`.

Справжні дерева Appium — від десятків кілобайтів до кількох мегабайтів і сутностей не мають,
тож обмеження не зачепить жодної нинішньої перевірки.

## Користувацькі історії

### US-1 (P1): Сервер не можна покласти UI-деревом

Як власник сервісу, я хочу, щоб жодне надіслане UI-дерево не зупиняло сервер, щоб один
зіпсований чи зловмисний запит не зупиняв перевірки всіх команд.

- **Чому P1:** це єдина critical-знахідка аудиту, без неї Vision не пройде сканер банку.
- **Незалежна перевірка:** надіслати знімок із деревом, що розгортається понад ліміт, і з
  деревом з оголошеними сутностями. Сервер відповідає на інші запити як завжди, знімок
  прийнято без дерева.
- **Сценарії приймання:**
  1. **Дано** дерево, що розгортається понад ліміт, **коли** автотест надсилає знімок, **тоді**
     знімок прийнято й порівняно як завжди, дерева в нього немає, а сервер записав попередження.
  2. **Дано** дерево з оголошенням сутностей, **коли** його надіслано, **тоді** сутності не
     розгортаються, знімок прийнято без дерева.
  3. **Дано** звичайне дерево Appium Android чи iOS, **коли** його надіслано, **тоді** усе
     працює, як раніше: структура, правила елементів, доступність.

### US-2 (P1): SDK не надсилає завелике дерево

Як автор автотестів, я хочу, щоб SDK сам не надсилав дерево понад ліміт і казав про це в лозі,
щоб тест не гнав мегабайти дарма й не падав через дерево.

- **Чому P1:** без цього завелике дерево щоразу їде через мережу, а людина не знає, чому в
  знімка немає аналізу.
- **Незалежна перевірка:** викликати `track` з деревом понад ліміт: у запиті немає дерева, у лозі
  попередження з назвою перевірки й розміром, результат перевірки такий самий, як без дерева.
- **Сценарії приймання:**
  1. **Дано** дерево понад ліміт, **коли** тест викликає `track`, **тоді** знімок надіслано без
     дерева, лог каже, яку перевірку й чому надіслано без дерева, тест не падає через це.
  2. **Дано** дерево в межах ліміту, **коли** тест викликає `track`, **тоді** запит такий самий,
     як раніше.

### US-3 (P1): SDK під назвою Vision

Як автор автотестів, я хочу підключати SDK і налаштовувати його під назвою Vision, щоб у коді й
конфігурації тестів не лишалось назви чужого продукту.

- **Чому P1:** вимога власника до поставки в банк; тестові проєкти оновлюються один раз, разом
  із лімітом із US-2.
- **Незалежна перевірка:** тестовий проєкт на новому jar з новими `import`, залежністю й
  змінними проходить ті самі перевірки з тими самими результатами; у лозі SDK немає «Visual
  Regression Tracker».
- **Сценарії приймання:**
  1. **Дано** тестовий проєкт, **коли** в ньому замінили залежність, `import` і назви змінних
     налаштувань на нові, **тоді** перевірки дають ті самі статуси й ті самі еталони, що й зі
     старим jar.
  2. **Дано** налаштування лише в старих змінних `VRT_*` чи у `vrt.json`, **коли** тест
     стартує, **тоді** SDK їх не бере й каже, яких налаштувань бракує.

## Граничні випадки

- Дерево рівно 10 МБ → приймається (REQ-040-01).
- Стиснуте дерево менше ліміту, а розгорнуте більше → знімок без дерева (REQ-040-02); сервер
  не розпаковує далі межі.
- Дерево не стиснуте й більше ліміту → те саме (REQ-040-02).
- Дерево з `<!DOCTYPE …>` без сутностей → теж без дерева (REQ-040-03): Appium такого не
  надсилає, і ризик розгортання тут не варто оцінювати.
- Дерево, що не є page source Appium → як і раніше, знімок без дерева (REQ-002-04).
- Знімок без дерева через ліміт на вкладці Accessibility → та сама підказка, що для знімка без
  дерева (REQ-003-15).
- Дерево надіслано через CLI чи MCP → ліміт сервера той самий (REQ-040-02); окремої перевірки в
  CLI немає.
- Старий jar SDK після оновлення сервера → продовжує працювати (запити ті самі, REQ-040-13), але
  власник вирішив його не підтримувати: тестові проєкти переходять на новий.
- В оточенні тесту лишились і `VRT_*`, і `VISION_*` → беруться лише `VISION_*` (REQ-040-11).

## Ключові сутності

- **UI-дерево** — page source Appium, що супроводжує знімок; розмір рахується в розгорнутому
  вигляді.
- **Ліміт дерева** — 10 МБ розгорнутого дерева, однаковий для сервера й SDK.

## Критерії успіху

| ID | Критерій |
|---|---|
| SC-040-01 | Знімок із деревом-бомбою (до 100 КБ стиснутого, понад 1 ГБ розгорнутого) приймається без дерева за ≤ 2 с, і паралельний запит до сервера за цей час відповідає за ≤ 1 с. |
| SC-040-02 | Сканер залежностей не знаходить critical чи high у бібліотеці розбору XML. |
| SC-040-03 | Контрольний сценарій проходить без змін еталона, крім назв SDK. |
| SC-040-04 | У jar SDK, його логах, змінних і файлі налаштувань немає назви «Visual Regression Tracker», `VRT_` чи `vrt.json`. |

## Припущення

- 10 МБ розгорнутого дерева з запасом покривають реальні екрани: найбільші page source Appium
  довгих списків — кілька мегабайтів.
- Тестові проєкти переходять на новий jar разом із запуском нової версії сервера (так вирішив
  власник), тож старі назви підтримувати не треба.

## Поза межами

- Ліміт розміру самого запиту зі знімком: він уже налаштовується на сервері й не змінюється.
- Перевірка розміру дерева в CLI і MCP: сервер і так обмежує дерево, а CLI надсилає по одному
  екрану.
- Інші класи SDK (`TestRunStatus`, `TestRunException`, `IgnoreAreas`): у них немає назви VRT.
- Переписування SDK з нуля — відкладено планом.
