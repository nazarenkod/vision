## Контекст і проблема

- **Вхід.** Vision вміє лише щось одне: або локальні акаунти, або LDAP, або SSO (OIDC). Банку
  потрібні корпоративний вхід для людей і локальні акаунти, яких немає в каталозі (технічні,
  підрядники). До того ж налаштування LDAP і SSO зараз не доходять до API з
  `docker-compose.demo.yml`: передається лише вимикач.
- **Перебір паролів.** Немає обмеження спроб входу ні для локальних акаунтів, ні для LDAP;
  перебір через Vision ще й блокує людям корпоративні облікові записи. Пароль локального акаунта
  може бути будь-яким непорожнім.
- **API.** Будь-яка помилка віддає stack trace з шляхами сервера (S-15); будь-який сайт може
  звертатися до API (CORS); документація API відкрита без входу; немає заголовків безпеки.

## Користувацькі історії

### US-1 (P1): Корпоративний вхід і локальні акаунти разом

Як адмін, я хочу, щоб люди входили корпоративним обліковим записом, а технічні й зовнішні —
локальним, щоб усі працювали в одному Vision.

- **Незалежна перевірка:** з увімкненим LDAP увійти і корпоративним акаунтом, і локальним, який
  створив адмін; з увімкненим SSO — кнопкою SSO і локальним акаунтом у формі.
- **Сценарії приймання:**
  1. **Дано** увімкнений LDAP і локальний акаунт від адміна, **коли** кожен входить своїм
     паролем, **тоді** обидва входять.
  2. **Дано** увімкнений SSO, **коли** людина відкриває сторінку входу, **тоді** бачить і кнопку
     SSO, і форму для локального акаунта.
  3. **Дано** людину з каталогу, **коли** адмін хоче створити їй локальний акаунт з тим самим
     email, **тоді** Vision не дає: акаунт уже корпоративний.

### US-2 (P1): Перебір паролів зупиняється

Як власник сервісу, я хочу, щоб після кількох невдалих спроб вхід тимчасово блокувався, щоб
пароль не можна було підібрати і корпоративні облікові записи не блокувалися через Vision.

- **Незалежна перевірка:** N разів увести хибний пароль: наступна спроба, навіть із правильним
  паролем, відмовляє до кінця блокування; у каталог LDAP запити не йдуть.
- **Сценарії приймання:**
  1. **Дано** N невдалих спроб для одного email, **коли** людина пробує ще, **тоді** отримує
     «спробуйте пізніше» і час, а Vision не звертається до LDAP.

### US-3 (P1): API не розказує зайвого

Як власник сервісу, я хочу, щоб API віддавало лише потрібне й лише своєму інтерфейсу, щоб
сканер безпеки банку не знаходив витоків.

- **Незалежна перевірка:** викликати API з помилкою, з чужого сайту, без входу до документації:
  без stack trace, без дозволу для чужого сайту, документація вимкнена.
- **Сценарії приймання:**
  1. **Дано** будь-яку помилку API, **коли** клієнт отримує відповідь, **тоді** там код,
     повідомлення й шлях запиту, без stack trace і внутрішніх подробиць.
  2. **Дано** сторінку іншого сайту, **коли** вона звертається до API з браузера, **тоді**
     браузер не дає їй прочитати відповідь.

## Граничні випадки

- Локальний акаунт адміна-майстра після відновлення ([013](../013-backups-and-secrets/spec.md)) —
  локальний, працює з LDAP/SSO (REQ-045-01).
- Блокування для email, якого немає → таке саме, як для наявного: не видно, чи акаунт існує
  (REQ-045-06).
- Вхід API-ключем (SDK, CLI) → обмеження спроб входу його не стосується; хибний ключ —
  відмова, як і зараз.
- Пароль, коротший за мінімум, у наявного акаунта → далі входить; змінити на короткий не можна
  (REQ-045-08).

## Поза межами

- Двофакторна автентифікація.
- Вхід через LDAP і SSO одночасно (обирається один корпоративний спосіб).
