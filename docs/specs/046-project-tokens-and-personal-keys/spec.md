## Контекст і проблема

Зараз у Vision є лише один вид ключа: персональний API-ключ людини. З ним працюють і автотести в CI
(SDK), і CLI та MCP. Це створює дві проблеми.

- **CI тримається на людині.** Ключ у CI команди належить комусь одному. Людина пішла з команди,
  її деактивували або вона створила новий ключ — і автотести всієї команди падають. Усі збірки з CI
  записані на неї, хоча запускала їх не вона. Ключ, що витік із CI, відкриває всі проєкти цієї
  людини.
- **Персональний ключ уміє замало.** З ним можна лише надсилати знімки й читати кілька речей.
  Погодити чи відхилити зміни, завести баг у Jira, додати правило елемента, переглянути збірки —
  лише після входу в інтерфейс. CLI й MCP через це не можуть виконати дію, яку людина й так має
  право зробити.

Під час переходу в банк кожен однаково створює новий ключ і оновлює CI (план, крок 6). Якщо
проєктні токени з'являться до цього, CI оновлять один раз.

## Користувацькі історії

### US-1 (P1): CI надсилає знімки проєктним токеном

Як QA-лід команди, я хочу видати автотестам токен проєкту, а не свій ключ, щоб CI не залежав від
конкретної людини і не мав доступу ні до чого, крім надсилання знімків у цей проєкт.

- **Чому P1:** без цього CI команди тримається на персональному ключі однієї людини.
- **Незалежна перевірка:** створити токен у налаштуваннях проєкту, вписати його в конфігурацію SDK
  без жодних інших змін і запустити автотест: збірка й знімки з'являються, автором збірки показано
  назву токена. Тим самим токеном спробувати переглянути збірки чи погодити зміну — відмова.
- **Сценарії приймання:**
  1. **Дано** токен проєкту A, **коли** автотест SDK стартує збірку, надсилає знімки й зупиняє
     збірку в проєкті A, **тоді** все проходить як з персональним ключем, а автором збірки
     вказано назву токена.
  2. **Дано** токен проєкту A, **коли** автотест надсилає знімки в проєкт B, **тоді** отримує
     відмову, у B нічого не створюється.
  3. **Дано** токен проєкту, **коли** з ним звертаються з CLI, MCP чи до будь-чого, крім запитів
     SDK, **тоді** отримують відмову з поясненням, що токен проєкту діє лише для SDK.
  4. **Дано** людину, що створила токен, **коли** її деактивували або забрали доступ до проєкту,
     **тоді** токен продовжує працювати.

### US-2 (P1): Керування токенами проєкту

Як editor проєкту, я хочу створювати, бачити й відкликати токени свого проєкту, щоб видати
кожному конвеєру CI окремий токен і відключити той, що витік.

- **Чому P1:** без керування токеном не можна ні видати, ні відкликати.
- **Незалежна перевірка:** створити два токени з різними назвами, побачити їх у переліку з датою
  створення й останнього використання, відкликати один: він більше не працює, другий працює.
- **Сценарії приймання:**
  1. **Дано** налаштування проєкту, **коли** editor з доступом до проєкту створює токен з назвою,
     **тоді** бачить токен повністю один раз; далі в переліку — лише назва, кінець токена, хто
     й коли створив, коли востаннє використано.
  2. **Дано** токен у переліку, **коли** editor його відкликає, **тоді** наступний запит з ним
     отримує відмову.
  3. **Дано** guest або editor без доступу до проєкту, **коли** відкриває налаштування проєкту чи
     звертається до токенів через API, **тоді** не бачить токенів і не може їх створити.

### US-3 (P1): Персональний ключ робить те саме, що людина в інтерфейсі

Як QA, я хочу з CLI, MCP чи власного скрипта з персональним ключем робити все, що мені дозволяє
роль у проєктах, до яких я маю доступ, щоб не відкривати інтерфейс для кожної дії.

- **Чому P1:** без цього CLI і MCP обмежені надсиланням знімків, хоча людина має більше прав.
- **Незалежна перевірка:** з ключем editor-а через API переглянути збірку, погодити зміну й
  завести баг у Jira: усе проходить, у журналі рішень і в Jira автором стоїть ця людина. З ключем
  guest-а: читання проходить, погодження — відмова.
- **Сценарії приймання:**
  1. **Дано** ключ editor-а з доступом до проєкту, **коли** через API погоджують зміну, **тоді**
     зміна погоджена від імені власника ключа, як в інтерфейсі.
  2. **Дано** ключ guest-а, **коли** через API читають збірки проєкту, до якого guest має доступ,
     **тоді** отримують дані; **коли** намагаються погодити чи змінити, **тоді** — відмова.
  3. **Дано** ключ людини без доступу до проєкту, **коли** звертаються до його даних, **тоді**
     відповідь «не знайдено», як у [042](../042-project-access/spec.md).
  4. **Дано** ключ деактивованої людини, **коли** з ним звертаються, **тоді** — відмова.
  5. **Дано** персональний ключ у конфігурації SDK, **коли** автотест надсилає знімки, **тоді**
     все працює, як і до цієї зміни.

## Граничні випадки

- Токен проєкту вписали в CLI → CLI отримує відмову з поясненням, що потрібен персональний ключ
  (REQ-046-03).
- Автотест з токеном проєкту A передає в налаштуваннях проєкт B → відмова, у B нічого (REQ-046-04).
- Збірку, яку стартував токен, зупиняє людина в інтерфейсі чи інший токен цього проєкту → як і
  зараз, за правами людини; токен може зупинити лише збірку свого проєкту (REQ-046-02, 04).
- Людина, що створила токен, пішла з команди → токен працює, у переліку лишається її ім'я як
  автора (REQ-046-06, 13).
- Відкликали токен посеред прогону CI → наступні знімки отримують відмову, вже надіслані
  лишаються (REQ-046-14).
- Дві однакові назви в одному проєкті → створення відхилено (REQ-046-11); у різних проєктах —
  можна.
- Guest з персональним ключем надсилає знімки → відмова, як і зараз: надсилати можуть лише admin
  і editor (REQ-046-20).
- Посилання на публічний звіт → працює як і раніше, без ключа ([042](../042-project-access/spec.md)
  REQ-042-12).
- Бекап і відновлення → токени проєктів потрапляють у бекап лише в незворотному вигляді, як
  персональні ключі; після відновлення CI працює.

## Ключові сутності

- **Проєктний токен** — належить одному проєкту; назва, кінець токена для впізнавання, хто й коли
  створив, коли востаннє використано, чи відкликано. Від імені проєкту, а не людини.
- **Персональний ключ** — належить людині; дає її роль і її доступ до проєктів.
- **Автор збірки** — людина (вхід або персональний ключ) або проєктний токен.

| SC-046-02 | Для кожного маршруту API є тест: проєктний токен отримує відмову всюди, крім запитів SDK. |

| SC-046-04 | Контрольний сценарій проходить, а новий крок показує CI з проєктним токеном і погодження з CLI персональним ключем. |

## Припущення

- Ролі лишаються глобальними (admin, editor, guest), як у [042](../042-project-access/spec.md).
- Токен проєкту не має ролі: його права — фіксований набір дій SDK.
- Live-події в інтерфейсі лишаються лише для тих, хто увійшов
  ([032](../032-authenticated-events/spec.md)).

## Поза межами

- Строк дії й автоматична ротація токенів: відкликання й новий токен вручну поки достатні.
- Обмеження прав персонального ключа (ключ лише на читання, ключ на один проєкт).
- Вимкнення персонального ключа в SDK налаштуванням — можна пізніше, коли команди перейдуть на
  проєктні токени.
- Журнал аудиту всіх запитів з токеном — окремою специфікацією, якщо його вимагатиме банк.
