## Контекст і проблема

Vision порівнює екрани з урахуванням UI-дерева: знаходить зсунуті елементи, невидимі зміни,
проблеми доступності, дає правила для елементів. Але дерево він розуміє лише з Appium (Android
та iOS). Тести вебу на Selenide надсилають лише скриншот, тож для них Vision — звичайне
попіксельне порівняння: зсув банера дає червоний екран, а доступність не перевіряється.

Просто передати HTML сторінки (`page source`) не вийде: у HTML немає координат елементів, а без
них Vision не знає, де на знімку кнопка. Потрібне дерево, зібране в самому браузері, з
положенням і розміром кожного видимого елемента.

## Користувацькі історії

### US-1 (P1): Веб-екран порівнюється за елементами

Як QA вебу, я хочу надсилати з тесту на Selenide знімок разом із деревом сторінки, щоб Vision
порівнював її так само, як мобільні екрани: зі зсувами, невидимими змінами й правилами для
елементів.

- **Чому P1:** без цього решта історій не має даних.
- **Незалежна перевірка:** тест відкриває сторінку, надсилає знімок з деревом; на наступному
  прогоні банер штовхає список униз → у Vision зсув розпізнано, список не позначено зміною.
- **Сценарії приймання:**
  1. **Дано** тест на Selenide, **коли** він надсилає знімок з деревом сторінки, **тоді** на
     порівнянні можна вибрати елемент на знімку, як на мобільному екрані.
  2. **Дано** на сторінці змінився текст кнопки, а пікселі — ні (той самий шрифт, той самий
     розмір рядка не міняється), **коли** приходить знімок, **тоді** зміна видна в розділі
     невидимих змін.
  3. **Дано** у проєкті правило «ігнорувати елемент `id:clock`», **коли** приходить вебсторінка з
     елементом `id="clock"`, **тоді** його зміна не позначається.

### US-2 (P2): Доступність вебсторінок

Як QA вебу, я хочу бачити проблеми доступності сторінки, як для мобільних екранів, щоб ловити
кнопки без підпису й низький контраст без окремих інструментів.

- **Чому P2:** цінно, але US-1 працює й без цього.
- **Незалежна перевірка:** сторінка з кнопкою-іконкою без `aria-label` → у Vision проблема
  «Елемент керування без підпису».
- **Сценарії приймання:**
  1. **Дано** кнопка без тексту й без `aria-label`, **коли** приходить знімок, **тоді** є
     проблема «Елемент керування без підпису».
  2. **Дано** поле вводу без `<label>`, `aria-label` і `placeholder`, **коли** приходить знімок,
     **тоді** є проблема «Поле вводу без підпису чи підказки».

### US-3 (P2): Дерево збирається одним викликом

Як автор тестів, я хочу отримати дерево поточної сторінки одним викликом SDK, щоб не писати
й не підтримувати власний скрипт збору.

- **Чому P2:** без нього US-1 можлива, але кожна команда писала б свій збір.
- **Незалежна перевірка:** у тесті на Selenide один виклик SDK дає дерево, яке Vision приймає.
- **Сценарії приймання:**
  1. **Дано** відкрита сторінка в Selenide, **коли** тест викликає збір дерева й передає його в
     `VisionOptions.uiTree`, **тоді** Vision приймає знімок з деревом.

## Граничні випадки

- Елементи в `iframe` і shadow DOM → [ПОТРЕБУЄ УТОЧНЕННЯ: збирати в першій версії, чи пропускати?].
- Прихований CSS (`display:none`, `visibility:hidden`, нульовий розмір) → не видимий, у порівнянні
  й доступності не бере участі (REQ-050-02).
- Липкий заголовок поверх прокрученого вмісту → координати за прокруткою на момент знімка
  (REQ-050-03).
- Велика сторінка (десятки тисяч вузлів, понад 10 МБ) → знімок без дерева (REQ-050-04).
- Сторінка ще вантажиться → дерево таке, як у момент виклику; стабільність — справа тесту, як
  і для Appium.
- Та сама сторінка в Chrome і Firefox → різні пристрої (браузери), різні еталони (001).

## Ключові сутності

- **Дерево вебсторінки** — видимі елементи з тегом, роллю, ідентифікаторами, текстом, доступною
  назвою, станом, положенням і розміром; масштаб сторінки й прокрутка на момент знімка.
- **Норма області дотику для вебу** — у CSS-пікселях, окремо від Android і iOS.

## Припущення

- Веб тестують на Selenide з Java, як і мобільні; інші мови й Playwright — пізніше.
- Скриншот робить той самий тест через Selenide, як зараз.

## Поза межами

- Playwright, Cypress і JS-SDK — лише Java + Selenide.
- Ручні перевірки вебу з CLI чи MCP (009) з деревом — пізніше.
- Перевірки, яких немає в мобільних правилах (порядок заголовків, мова сторінки, ARIA-атрибути) —
  окрема специфікація.
