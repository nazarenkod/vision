# Специфікації

Специфікація — контракт фічі: що система повинна робити, для кого і як це перевірити. Підхід
поєднує [GitHub Spec Kit](https://github.com/github/spec-kit) (історії з пріоритетами, незалежна
перевірка, критерії успіху, маркери уточнень) і [Kiro](https://kiro.dev/docs/specs/concepts)
(вимоги в нотації EARS, дизайн і задачі окремими файлами). Порядок роботи — в
[agentic-workflow](../guides/agentic-workflow.md).

## Папка фічі

```
docs/specs/NNN-коротка-назва/
├── spec.md     що і навіщо: історії, вимоги EARS, граничні випадки, критерії успіху     (людям і агентам)
├── design.md   як: підхід, компоненти, дані, ризики; «Перевірка вимог» — тест на кожну  (інженерам)
└── tasks.md    кроки реалізації з чекбоксами; [P] — можна паралельно                   (для нової роботи)
```

`spec.md` не містить деталей реалізації: файлів, таблиць, бібліотек. Вони живуть у `design.md`,
тому специфікацію читає й затверджує власник продукту, а дизайн змінюється без переписування
вимог. Шаблони — у [_template](_template/), skills — `/spec`, `/design`, `/verify`.

## Статуси

| Статус | Що означає | Хто переводить |
|---|---|---|
| `Draft` | пишеться; є `[ПОТРЕБУЄ УТОЧНЕННЯ]` | автор |
| `Approved` | вимоги погоджені; можна писати дизайн і реалізовувати | власник продукту (зараз — Дмитро Назаренко) |
| `Implemented` | код злитий; кожна вимога має тест або `manual:` у `design.md` | автор реалізації |
| `Verified` | сценарії приймання пройдено на стенді (реальна Jira, реальні пристрої) | QA |

Замінену специфікацію не видаляємо: у полі «Статус» лишається останній статус, а в «Пов'язане» —
посилання на нову.

## Вимоги

- ID `REQ-NNN-NN`, де `NNN` — номер специфікації. ID не перевикористовуємо; складну вимогу
  розбиваємо на нові ID, а не перенумеровуємо.
- Кожна вимога посилається на історію (`US-N`) і описує одну перевірювану поведінку.
- Нотація EARS:

| Шаблон | Коли |
|---|---|
| СИСТЕМА ПОВИННА … | завжди |
| КОЛИ <подія>, СИСТЕМА ПОВИННА … | реакція на подію |
| ПОКИ <стан>, СИСТЕМА ПОВИННА … | поки триває стан |
| ЯКЩО <небажана ситуація>, ТО СИСТЕМА ПОВИННА … | помилки, збої, зловживання |
| ДЕ <налаштування чи опція>, СИСТЕМА ПОВИННА … | залежить від конфігурації |

- Без «швидко», «зручно», «за потреби», «тощо». Числа — з одиницями.
- Невідоме — `[ПОТРЕБУЄ УТОЧНЕННЯ: питання]`. Зі специфікацією, де лишився такий маркер, у
  `Approved` не переходимо.

## Трасування

`design.md` → «Перевірка вимог»: кожна вимога → тест у форматі `` `шлях › назва тесту` ``
(назву можна обрізати «…») або `manual: що зробити й що побачити`. `scripts/check-docs.py`
перевіряє, що вимоги унікальні й простежені, а названі тести та шляхи існують. Перейменуєш
тест — перевірка про це скаже.
