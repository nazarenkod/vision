# Специфікації

Специфікація описує, **що** система повинна робити і **навіщо**, так, щоб це можна було
перевірити. **Як** це зроблено (план) і **кроки** (задачі) лежать поруч, в окремих файлах.
Порядок роботи — у [agentic-workflow](../guides/agentic-workflow.md).

## Папка фічі

```
docs/specs/NNN-коротка-назва/
├── spec.md    що і навіщо: вимоги, критерії приймання, трасування на тести   (обов'язково)
├── plan.md    як: дизайн, зачеплені модулі, міграції, ризики                  (для нової роботи)
└── tasks.md   кроки реалізації з чекбоксами, кожен — з перевіркою             (для нової роботи)
```

Для вже реалізованих фіч (001–012) дизайн коротко описано в самій `spec.md`, а `plan.md` і
`tasks.md` немає: вони свою роль уже виконали. Шаблони — у [_template](_template/).

## Статуси

| Статус | Що означає | Хто переводить |
|---|---|---|
| `Draft` | пишеться, є відкриті питання | автор |
| `Approved` | вимоги погоджені, можна планувати й реалізовувати | власник продукту (зараз — Дмитро Назаренко) |
| `Implemented` | код злитий, тести на вимоги є | автор реалізації |
| `Verified` | перевірено на стенді (реальна Jira, реальні пристрої) | QA |
| `Superseded by NNN` | замінено іншою специфікацією | автор нової |

## Як писати вимоги

- Одна вимога — одна перевірювана поведінка, з ID `REQ-NNN-NN`. ID не перевикористовуються.
- Формат EARS:
  - завжди: «СИСТЕМА ПОВИННА …»;
  - подія: «КОЛИ <подія>, СИСТЕМА ПОВИННА …»;
  - стан: «ПОКИ <стан>, СИСТЕМА ПОВИННА …»;
  - небажане: «ЯКЩО <ситуація>, ТО СИСТЕМА ПОВИННА …»;
  - опція: «ДЕ <налаштування>, СИСТЕМА ПОВИННА …».
- Без «швидко», «зручно», «за потреби»: лише те, що можна перевірити тестом або на стенді.
- Кожна вимога в розділі «Трасування» має тест (`файл › назва тесту`) або позначку
  `manual: <як перевірити>`.
